# 工具调用是一条**可量测的臂，默认关**

「MCP / 工具集成」（评分表 #6）那句原话是「通过 MCP 协议**或** Function Calling」。
前者是**别人调我们**（[ADR-0012](0012-mcp-server-handwritten-jsonrpc.md)），
后者是**我们自己的模型调工具**。这一份是后者的决定：**实现了、量过了、默认关**。

★ 它与 [ADR-0005](0005-model-choice-by-measurement.md)「选型由实测拍板」是同一个形状：
一个新能力**不因为"它更先进"就该开**，而因为**在同一批输入上量出来的数更好**才该开。
量不出来就保持关——**代价是确定的，收益不是**。

## 实现的是什么

- `src/lib/engine/tool-loop.ts`：模型要调工具就调、把结果喂回去、直到它给出答复
  （四条边界各有处置，见 `docs/known-tradeoffs.md` 与工单 06）。
- `src/lib/plan-tools.ts`：四件工具（`search_past_stories` / `read_shelf` /
  `check_draft` / `character_brief`），**与生产同一处实现**。
- `providers/openai-text.ts`：`tools` / `toolChoice` / `messages` 三个**可选**字段。
  ★ **`tool_choice` 只提供 `auto` 与 `none`**：强制点名实测不可依赖
  （`scripts/probe-tool-calls.mts` 格 B，同一请求体十次里七次 400），所以适配器不给调用方那个选择。
- 新事件 `{kind:'tool'}`：进「编故事」那一格（与 `retrieved` 同一条处置，不占阶段轨）。

## 三臂对照（2026-10-19，`--books=5`）

```
node scripts/rag-bakeoff.mts --books=5 --arms=off,lexical,tools
```

| 臂                                  | 通过 | 一次过 | 平均重试 | 平均每本调用工具 | 中位耗时 |
| ----------------------------------- | ---- | ------ | -------- | ---------------- | -------- |
| `off`（不检索）                     | 5/5  | 5/5    | 1.00     | —                | ≈11 s    |
| `lexical`（预先检索，今天线上那条） | 5/5  | 5/5    | 1.00     | —                | ≈11 s    |
| `tools`（模型自选）                 | 5/5  | 4/5    | 1.40     | **4.0**          | ≈21 s    |

**三条读数，一条比一条硬：**

1. **每本都恰好调用 4 次工具**（4.0 是平均值，逐本看是 `4 / 4 / 4 / 4 / 4`）——
   而 4 就是 `maxSteps` 的上限。也就是说：**模型从不自己停手**，
   它每一本都会一直查、查到预算被拦为止。"让它自己决定要不要查"这句话在实测里的答案是
   "它决定每次都要查、并且查满"。
2. **通过率上分不出差别**。`tools` 4/5 一次过，另外两臂 5/5——**差一本**。
   而 n=5 上**一格就是 20 个百分点**，预声明的门槛是 10 个百分点。
   也就是说：**这道门槛在这个规模上数学上达不到**，本轮的最小可检测效应 MDE ≈ 20 pp。
   这不是"没试"，是"试了、并且算出了这个设计能看见多大的差"
   （B1 那一轮为同一个教训付过学费：门槛是拍出来的、不是量出来的）。
3. **代价是确定的**：每本多 4 次文本调用（规划那一步的 4–5 倍），耗时约翻倍。

**结论：默认关。** 不是"工具没用"——是**这一轮的规模看不见它有没有用，而它的代价看得见**。

## 翻案条件（写清楚，别留给下一个人猜）

任何一条成立就可以重开这一栏，并且这一次**先把门槛按规模算出来**：

- 把 n 提到 ≥50/臂（那时一格是 2 pp，10 pp 的门槛才真的有判别力）；
- 或者换一个**一次通过率本来就不高**的语料/模型——今天三臂都是 5/5，
  天花板效应把差别压在下面了（`off` 臂在更早一轮是 10/10 里的 8/10，可见别处有空间）；
- 或者把"值得量"的那个量从通过率换成**别的**：工具调用的正当性可能不在"故事表更合法"，
  而在"检索的**剂量**由模型按需决定"（比如很新的主题下 `lexical` 会白注一段无关的范例，
  而 `tools` 可以一次都不调）。**那要用一个会区分这两件事的判据**，不是通过率。

## 一处被这一轮量出来的实现缺陷（已修）

第一轮 `tools` 臂平均每本调了 **4.8** 次，而轮数上限是 4——**4.8 > 4 只可能是并行调用**
（一轮里回多个 `tool_calls`）。也就是说"步数预算"在那条路上根本没有它看起来那么严。
修法是适配器在带工具时发 `parallel_tool_calls: false`（探针格 H 已验过这个参数回 200）；
修完之后读数变成**恰好 4.0**。

★ 这一条值得单独记：**一个"看起来在管预算"的参数，可能管的不是你以为的那个东西。**
"轮数上限"与"调用次数上限"是两个量，而我第一版把它们当成了一个。

- Status: accepted
- Considered Options: 让模型自选工具并**开成默认**（看上去更"Agent"，
  但代价确定、收益没量出来）；**实现、默认关、（工单 08 的）三臂对照量不出来就保持关**（选中）；
  不做 Function Calling（评分表 #6 那半个词就落空了，而实现成本已经很低）
- Consequences: ① `planStory` 里 `tools` 与 `retrieve` **互斥、同时给当场抛**——
  它们是同一个问题的两种答案，两个都给会让这一臂量的是"检索了两次"；
  ② `tools` 与 `onDelta`（流式）也互斥：工具循环要完整回包；
  ③ **默认关**，所以脚本与跑测那两条路上的请求体**逐字节不变**（判据 8 有单测钉住）；
  ④ `.env.example` 的 `LLM_JSON_MODE` 那一段记了实测：`tools` 与 `response_format`
  **不互斥**（两档都过），所以这一档不必放弃 JSON 强制
