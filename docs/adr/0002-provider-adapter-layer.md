# AI 供应商一律走「能力适配层」，环境变量按能力命名而不按厂商命名

`lib/engine/` 里每个能力（规划文本 / 生成图像 / 合成语音 / 视觉比对）定义一个**能力接口**，
每家供应商是它的一个适配器，运行时按环境变量选择。`.env.example` 因此写的是
`LLM_API_KEY` / `IMAGE_API_KEY` / `TTS_API_KEY` 加各自的 `BASE_URL`，**不出现任何厂商名**。

这条不是整洁癖，是「平台而非聚合」那句主张的技术落点：换一家模型供应商应当只改
`.env.local` 的值与一个适配器文件，**不动引擎、不动组件、不动数据库**。
反过来，如果引擎里直接 `import` 各家的 SDK，产品就成了「一堆工具的串联」——
而评委要看的恰恰是这个区别（技术方案创新 8 分）。第二个理由更硬：
W1 的模型对比实测要求**同一套提示词与同一批测试用例在候选之间横评**，
接口不统一就没法横评，只能写三份胶水代码。

代价要说清：多一层间接，出错时堆栈里多一跳；某家独有的能力（比如参考图权重、
音色解绑接口）必须抽象成接口的一部分，否则会被"临时开个后门直接调 SDK"侵蚀掉——
**这条要守住，它就是接口存在的意义**。

- Status: accepted
- Considered Options: 直接用各家官方 SDK（起步快，但把供应商焊进引擎，且横评要先写三遍胶水）；用 Vercel AI SDK 统一（见 [ADR-0004](0004-no-vercel-ai-sdk.md)）
- Consequences: 适配器要覆盖「删除/解绑」这类非生成类的生命周期方法——隐私设计里
  「删孩子时调厂商 API 解绑 voice_id」是交付承诺，不是可选项
