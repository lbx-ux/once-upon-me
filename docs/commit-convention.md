# 提交规范

> 适用于本仓库全部提交。目的很单纯：让评审（和三个月后的自己）能读懂这个仓库是怎么一步步长出来的，而不是一坨一次性倒进来的代码。

---

## 一、消息格式

```
<type>(<scope>): <subject>
                              ← 空行必填
<body：为什么这么做、取舍是什么>
                              ← 空行必填
<footer：可选>
```

三段里只有 `type(scope): subject` 是必需的。**subject 和 body 之间必须有空行**，否则 `git log --oneline` 会把 body 的第一行当成标题截走。

### type

| type       | 用在哪                                            |
| ---------- | ------------------------------------------------- |
| `feat`     | 新功能、新页面、新组件、新引擎步骤                |
| `fix`      | 修 bug（说清症状与成因）                          |
| `refactor` | 不改外部行为的结构调整                            |
| `perf`     | 只为了性能/体积的改动（如图片、懒加载、重绘范围） |
| `docs`     | README、注释、文档                                |
| `style`    | 纯格式（Prettier / ESLint 自动修复），不动语义    |
| `build`    | 构建链、依赖、`package.json` 脚本、pnpm 配置      |
| `ci`       | CI 工作流                                         |
| `test`     | 测试                                              |
| `chore`    | 其余杂项（`.gitignore`、目录整理等）              |

### scope

用**目录或模块名**，不要用个人偏好词。当前有效值：

`scaffold` `tokens` `hero` `art` `home` `themes` `docs` `scripts`

后续按 [README 的预留结构](../README.md) 增加：`engine` `prompts` `schemas` `store` `creation` `reader` `panels` `mcp`。

一次改动跨多个 scope 时，**优先拆提交**；拆不开就不写 scope，别写 `misc` 这种空词。

### subject

- 中文，**不超过 30 字**，动词开头（`新增` / `修复` / `收紧` / `替换`）。
- **结尾不加句号**——和首屏文案同一规矩。
- 不写「修改」「更新」「优化」这类没有信息量的词；要说改出了什么结果。
- 不复述文件名（diff 里已经有），说意图。

### body

- 回答**为什么**，不是改了什么（`git diff` 已经说明了什么）。
- 有取舍的必须写取舍：放弃了哪条路、代价是什么。
- 每行不超过约 36 个汉字（72 字符），列表用 `- `。
- 修 bug 的写清症状 + 成因，别只写「修好了」。

### footer

- 破坏性改动：`BREAKING CHANGE: <说明>`
- 关联 issue：`Refs: #123`
- AI 协作署名（可选，本项目默认带）：`Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`

## 二、提交前必过

```bash
pnpm format:check && pnpm lint && pnpm typecheck
```

三条全绿才提交。任何一条红了就当场修，不要留「先提交再修」的脏历史——评审会看。

## 三、粒度

- **一个提交一件事**。改组件顺手动了令牌，就拆成两个提交。
- 完成一个可交付的小步就提交，不要攒到周末一次倒进去。
- 中间状态想存：用 `git stash` 或开 WIP 分支，不要用「临时提交一下」污染主线。
- **唯一的例外是首个提交**：工程骨架是一次性立起来的，拆成几个提交反而要靠
  猜测还原中间状态。它之后的一切按上面三条走。
- 不要回填日期（`GIT_AUTHOR_DATE` / `--date`）。拆提交是正当的，伪造时间线
  不是——author 与 committer 时间不一致，`git log` 里一眼可见。

## 四、不许进仓库的东西

| 项                                  | 处理                                                                               |
| ----------------------------------- | ---------------------------------------------------------------------------------- |
| `.env.local` 及任何真实密钥         | `.gitignore` 已排除；公开仓库里提交出去的密钥撤不回来                              |
| `node_modules/` `.next/` `out/`     | 已排除                                                                             |
| `*.tsbuildinfo` `next-env.d.ts`     | 已排除                                                                             |
| `.claude/`                          | 已排除（本地工具配置，与作品无关）                                                 |
| 任何**本机绝对路径**（如 `E:\...`） | 禁止出现在代码、注释、文档、提交信息里——评审看不到那台机器，引用必须对陌生读者自洽 |

首次提交前务必确认：

```bash
git status --short
```

列出来的每一项都应该是**打算公开的源码或素材**。看到 `.env`、绝对路径、个人文档，立刻回去补 `.gitignore`。

## 五、不要伪造历史

把当前这棵树按逻辑层拆成几个提交是正当的（本来就是几件不同的事）；**但不要用 `GIT_AUTHOR_DATE` / `--date` 回填日期**去模拟「按周推进」。这种造假在 git 里盖不住——对象的写入时间与作者时间对不上，`git log` 一眼看得出来；而一旦被认定，整个作品的资格都没了。

真实开发过程从**下一个提交**开始记录就够了。

## 六、分支与身份

- GitHub 默认分支是 `main`。本地现在是 `master`，推送前改一下：`git branch -M main`
- 提交作者用真实姓名与邮箱，评委会看 `git log` 的 author：

```bash
git config user.name "你的姓名"
git config user.email "你的邮箱"
```

- 仓库要 **Public**（或至少给评审加访问权限），否则对方根本打不开。
