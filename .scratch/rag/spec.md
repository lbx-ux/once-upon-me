## 零、一句话

**给引擎接上一件它今天没有的能力：在写之前，先把「已经写过的、与这次请求最近的」找出来，
分正反两面注进提示词——正例给节奏与用词，反例明令避开。**

不是套一层向量库的壳。这一份的重点全在**语料选得对不对**与**增益量不量得出来**。

## 一、判据（先说怎么算做完）

官方原话是「是否实现 RAG 架构，**检索策略是否合理**，生成质量是否因检索增强而
**显著提升**」。所以判据必须是**对比**，不是「用上了」。六条，全部可复现：

| #   | 判据                                                                                            | 怎么验                                                                   |
| --- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 1   | 引擎硬约束不许破：不联网、不启浏览器仍能跑完一本书                                              | `node scripts/engine-run.mts --mode=stub` 退出码 0                       |
| 2   | 索引可从语料重建且**指纹可复现**（同输入同指纹）                                                | `node scripts/build-rag-index.mts` 连跑两次，两次指纹一致                |
| 3   | 检索器是**纯函数**，边界有单测：约束过滤、打分排序、top-k、阈值、**空结果是合法结果**、负向检索 | `pnpm test` 里的 `rag/retrieve.test.ts`                                  |
| 4   | **开/关检索各跑一遍**，同一批主题 × 10 本，出增益表                                             | `node scripts/rag-bakeoff.mts --books=10` → `.out/rag-bakeoff/report.md` |
| 5   | 审核落点：10 条故意越线**全部拦下且原因具体到条款**；10 条正常**零误拦**                        | `node scripts/review-cases.mts`（工单 05），两列都逐条打印               |
| 6   | 出处可见：工作台运行视图看得见「检索到 n 条」，成品书上点得开来源                               | 手验一次 + 截图进 `docs/screenshots/`                                    |

★ **判据 4 的预声明阈值**（先写在这里，免得跑完再挑口径）：
**Schema 一次通过率 +10 个百分点** 或 **平均重试次数 −0.3**，二者取其一即算「显著」——
与 `docs/tech-selection.md` §9 「差距超过 10 个百分点」同口径。
**达不到就如实写「在这份语料上不显著」**，并把差异与量法写进技术文档。
这一条是这份 spec 最要紧的一句：把向量库摆在那儿不叫得分，量出增益才叫。

## 二、现状与事实（都是量出来的，不是印象）

1. **全仓零检索**。`package.json` 运行时依赖只有 `gsap / next / react / react-dom / sharp`：
   没有向量库、没有 embedding 调用、没有语料。
   `src/lib/prompts/story-plan.ts:32` 把**适龄档**说成「#3 那一栏的对照物」——
   那是**分档**（按年龄取一条规则），不是检索：无语料、无索引、无 top-k、无可对比读数。
   `src/lib/engine/domain.ts:64` 那句「checklist #3 的验收就靠它分档」同上。
2. **角色卡被读出来注入两个调用**这件事是真的（`illustrate.ts` 的锁脸输入与核对清单同源），
   评分文档已经识破过一次「把它重新包装成 RAG」的尝试。**本特性不许再包装第二次。**
3. **种子语料的真实体量**（2026-10-19 实测，一行脚本可复现）：

   ```
   node -e "读 src/components/booklist/books/*.ts，数引号里的正文"
   → 12 本 · 96 跨页 · 正文 6031 汉字 ≈ 4.3k token
   ```

   ★ **这个数字决定了一半设计**：4.3k token 一次全塞得进上下文。
   所以「12 本样书」**不构成** RAG 的正当性，它只是**种子**。
   检索的正当性只能落在下面第三节那份**必须检索**的语料上。

4. **`/embeddings` 已量（2026-10-19，工单 01）：路由**活着**，但这把 key 上没有任何可用的嵌入模型。**
   三行判据，全部来自一次真实请求（`node scripts/probe-embeddings.mts`，可重跑）：

   | 实验                                             | 结果                                                                                | 读出来的话                                      |
   | ------------------------------------------------ | ----------------------------------------------------------------------------------- | ----------------------------------------------- |
   | 对照组：**不存在的路径**                         | `404 · NOT_FOUND · 接口不存在`                                                      | 「没有入口」在这条网关上的原始形状              |
   | 判别实验：**确定存在的对话模型**打 `/embeddings` | `400 · MODEL_CAPABILITY_NOT_SUPPORTED · 当前模型不支持该能力：embeddings`           | **与上一行不同形 ⇒ 路由是活的**，这是模型级拒绝 |
   | 目录里 **26 个已服务模型**逐个打                 | 0 个 200；25 个 `CAPABILITY_NOT_SUPPORTED`、1 个 `ACCESS_DENIED`（`neohorse-1-9b`） | 已服务的名字里没有一个能做嵌入                  |

   ★ 于是这条 spec 的**架构随之简化**（不是砍需求，是砍掉一件不存在的能力）：
   **只有词法档，没有混合档**；不写 `providers/embeddings.ts`、不写 `Retriever` 接口、
   `.env.example` 里不加 `EMBEDDING_*`——**不写一个用不上的配置项**
   （同一条纪律：`example-wishes.ts` 里那句「留一个没人读的表，下一个改的人会漏改它」）。
   ★ `neohorse-1-9b` 那一格**是空的，不是否定的**：没开通就问不出它的能力。
   去控制台看一眼它是不是嵌入模型——是的话开通之后混合档就有了（那是**换档条件**，不是今天的结论）。
   ★ 探针第一版**骗过我一次**，记在工单 01 的 Comments 里：连打几十次之后网关开始限流，
   汇总把 `RATE_LIMITED`（**什么都没证明**）与 `CAPABILITY_NOT_SUPPORTED`（有结论的否定）
   加成了一个数，还照样下了全称否定。这是 W1「把『没测成』记成『测出来』」换了个马甲。

## 三、语料：三份，归属与落点**各不相同**

★ 这一节是整份 spec 最容易做错的地方。三份语料不是「同一个库的三个目录」——
它们的**归属**不同，于是**落点、许可、检索时的过滤条件**全都不同。

| 语料           | 是什么                                                   | 归属         | 落在哪                                                         | 份量                    |
| -------------- | -------------------------------------------------------- | ------------ | -------------------------------------------------------------- | ----------------------- |
| **① 种子**     | 12 本样书的跨页（`caption` + 正文）                      | 仓库资产     | `src/lib/rag/index.seed.json`（生成物，随仓库提交）            | **96 跨页 · 39.0 kB**   |
| **② 创作史**   | 这个家庭已经生成过的书：`books/<id>/story.json` 的每一页 | **用户私有** | `ASSET_ROOT/u/<userId>/books/`（**不建持久索引**，见下）       | 每本 ≈20 页，随使用增长 |
| **③ 审核条款** | 红线条款 + 适龄约束，一条一个 chunk，带类别与处置        | 仓库资产     | `src/lib/rag/review-corpus.ts`（**代码即语料**，不是外部数据） | 先 40–60 条，会长       |

★ **`docs/*-art-prompts.md` 的画面提示词段推迟了**（原表把它算在 ① 里）。理由不是来不及，
是**它今天没有消费者**：本轮接的是规划（吃正文）与审核（吃条款），出图那条按 §六 本轮不接。
往索引里塞一类没人读的 chunk，下一个改语料的人得替它猜用途（`example-wishes.ts` 里
「留一份没人读的表，下一个改句子的人会漏改它」是同一条纪律）。
接出图那条时再加 `kind: 'prompt'`，那时它有明确的消费者与过滤条件。

三条纪律：

- **② 的索引一个字节都不进仓库，检索时必须带 `owner` 过滤。**
  不这么做，症状是「别人家孩子的书正文被喂进了这个模型的上下文」——
  与仓库现有的「别人的书 id 在你那一片里不存在 → 404」是同一条纪律，
  而它比 404 严重得多（那是读不到，这是**读到了别人的**）。
- **② 不建持久索引，检索时现场扫。** 理由是量级（与 ADR-0007 的
  「`summaries()` 是一次前缀扫描，量级到几千张卡要换实现」同一条纪律）：
  几十本 × 20 页 ≈ 数百条，读盘 + 切块 + 词法打分为毫秒级。
  几百本以后再换实现，那时换成什么由当时的量决定，现在不预设。
  ★ 落盘还有第二个代价：**索引与书不同步**是必然会发生的一件事
  （删一本书、改一版草稿），而「检索到一本已经不存在的书」是这个功能最难查的坏法。
- **③ 不混进 ①②。** 条款是**规则**，每次都必须用全；
  拿检索去「检索」一条你知道一定要用的规则是糊弄。
  ③ 真正的检索形态是「拿**这一页的文本**去取**适用条款的子集**」（工单 05）。

### 切块口径

- **跨页 / 页 = 一个 chunk**（不是滑窗）。一页正文 1–3 句、几十字，
  天然就是一个语义单元，**滑窗在这个粒度上没有意义**——这是本语料量级下的简化，写进球头。
- 每个 chunk 的元数据固定五项：`kind`（本轮只有 `spread` / `page`；条款不在这份索引里）、
  `ageBand`、`theme`、`form`、`owner`（`'library'` 或 `u/<userId>`）。
  前四项是**硬过滤**的键，不是打分的特征。
  ★ 元数据里的「不限」写作 `'*'`，它是**通配**（对谁都开放），不是「不知道」——
  「不知道」要在切块时就填清楚：`chunksFromStoryBook` 缺哪个填哪个，
  **不许把"没有"填成一个像样的默认值**（空值不等于默认值，这个项目在这条上付过学费）。
  ★ 样书的 `form` 就是 `'*'`，而且**不是"没记"**：样书是线性的，但它在这里的作用是
  「同一个年龄档下**写完了的句子**长什么样」——句子与节奏与形态无关。
  标成 `solo` 的后果很具体：共读版那一半请求按 `form` 过滤之后一条都取不到，
  **半个产品的检索是哑的**。形态约束真正要管的是避重那一侧，那条落在 ② 的 chunk 上。
- chunk 的 `text` 是**给模型看的那段字**；出处标识（书名 / 页码 / 条款号）另存，
  **不进 text**——理由见 §六 那条红线。

## 四、架构（贴着仓库既有的三条纪律落）

```
src/lib/rag/                     ★ 新目录。纯函数为主，不 import React（ESLint 那道禁令要加进白/黑名单）
├─ corpus.ts        语料装载与切块：三个来源 → 同一个 RagChunk（纯函数）
├─ retrieve.ts      ★ 纯函数：约束过滤 → 打分 → top-k → 阈值。单测的主战场
├─ score.ts         词法打分：中文字符 bigram + BM25（**只有这一档**，见 §二.4）
├─ review-corpus.ts ③ 审核条款（代码即语料）
├─ prompt.ts        检索结果 → 提示词那一段（带出处标识，正反两栏）
└─ index.seed.json  ① 的索引（生成物，文件头注明「改了源要重跑 build-rag-index」）

scripts/
├─ build-rag-index.mts   建 ① 的索引 → src/lib/rag/index.seed.json
├─ rag-bakeoff.mts       开/关检索对照跑测 → .out/rag-bakeoff/
└─ review-cases.mts      工单 05 的 10 + 10 条
```

★ **能力层里一个文件都不加**（§二.4 已量：这把 key 上没有嵌入模型）。
`providers/types.ts` 不加 `Retriever`、不加 `embeddings.ts`、不加 `EMBEDDING_*`——
**不写一个用不上的接口**：它一旦存在，下一个人会以为有条向量档可以配。

四个取舍，每个都由仓库自己的纪律推出来：

1. **检索策略 = 结构化硬过滤 + 词法打分（bigram-BM25）。** 只有一档，
   所以**没有融合那一步**——RRF 是为两份排序准备的，一份排序做 RRF 是自欺。
   这一档同时满足 `engine-run --mode=stub` 那条硬约束（不联网跑完一本书），
   而它今天**不是兜底，是唯一档**（§二.4）。
2. **中文用字符 bigram，不按词切。** 中文没空格，而引 jieba 之类的分词器
   是给这个量级（几百条）上重装备。bigram + BM25 的公式在零依赖下给出可解释的排序。
   ★ 这一条写进技术文档时也是「检索策略是否合理」的正答：**说得清为什么这么做**。
3. **索引是一个 JSON 文件，不引向量数据库服务。**
   pgvector / Milvus / Qdrant 都要求动部署（生产是同机四件），而这里的数据量是
   **数百条**。同一条判断在 ADR-0004（不引 Vercel AI SDK）与 ADR-0007（不为角色卡建库）里
   已经做过两次，这里是第三次。
   ★ 今天它更硬：**连嵌入都要不到**（§二.4），引一个向量库只会是一个空壳。
4. **不新起一条平行流水线。** 改的是 `planBook` 的**入参**与提示词的**一段**
   （README §五 记过那次教训：横评脚本自己搭一条平行路，量出来的数「不是引擎要用的那个数」）。

**引擎硬约束的落点**：`src/lib/rag/` 与 `src/lib/engine/` 同档——
`eslint.config.mjs` 里那条禁 `react` / `next/*` / `@/components/**` / `window` / `document`
的规则要把它一起罩住，验收仍是那条 `engine-run --mode=stub`。

## 五、检索策略（这一节就是「检索策略是否合理」的答卷）

```
查询 = (孩子年龄档, 主题, 形态, 这次的 wish/reviseNote, 已生成草稿? )
         │
         ├─ 1. 硬过滤（两个极性的强度**不同**，见下表）
         │     ★ 过滤不命中就是空集，**空结果是合法结果**，不许兜底成「随便给几条」
         │
         ├─ 2. 打分：中文字符 bigram 倒排 + BM25（k1=1.2, b=0.75），一份排序
         │     （★ 没有融合那一步：只有一档排序，做 RRF 是自欺，见 §四 取舍 1）
         │
         └─ 3. 取 top-k（k=3）+ 阈值（低于阈值宁可返回空）
```

★ **k 与阈值定稿了（2026-10-19，工单 06 的对照跑测）**：`k=3` · `minScore=2`——
**就是原来的默认值，没有改**。扫描量到的是：`k=1` 平均 1.0 条范例、`k=3` 2.1 条、
`k=5` 2.3 条（边际递减，取 3 那个拐点）；`minScore=1` 时 10/10 个主题取得到范例、
`2` 时 6/10、`3` 时 4/10。`minScore=1` 看着更"能用"，但**两臂各跑一轮（各 10 本）之后，
没有任何一个量给出可复现的差异**，而且它多取到的那一簇（约 1.5 分）是"只命中一个常见
bigram"的段落——**它们的相关性这五个量看不见**。所以没有一格的读数足以替换默认值；
`minScore=1` 记成下一轮的第一个候选。全部读数在 `src/lib/rag/load.ts` 那两个常量上方
与 `.out/rag-bakeoff/report.md`。

**两个极性的过滤强度不同**（这一格是工单 03 落地时才定准的，原稿只写了「具体值必须相等」）：

| 极性      | owner        | ageBand                  | theme                                  | form         |
| --------- | ------------ | ------------------------ | -------------------------------------- | ------------ |
| `example` | 库 + 自己    | 同档或**相邻一档**或通配 | 同主题或通配（**主题要先归一**，见下） | 同形态或通配 |
| `avoid`   | **只取自己** | 不过滤                   | 不过滤                                 | 同形态或通配 |

- **`example` 收相邻一档**（偏离原文那句"必须相等"，理由要记住）：库里的 96 条**全是
  `4-6`**（12 本样书的主角都写着"约 5 岁"）。只收同档的后果是——一个 7 岁孩子的请求
  **一条范例都取不到**，于是这一栏对四个年龄档里的三个是**哑的**，而那恰恰是最该有作用的场景。
  "相邻"与"隔两档"的区别是实打实的：4 岁档的句子给 8 岁看是**错的**参考
  （样书的用词本来就跨这两档：每行 ≤22 字，与 `AGE_RULES` 里 `4-6` 的 12–18 字、
  `6-8` 的 18–26 字都相容）。原文那句警告防的是「8 岁档的句子漏给 4 岁档」，这一条仍然防着。
- **`avoid` 反过来全都不过滤**：它的语义是「**这个孩子已经读过了**」。读过就是读过——
  上个月读的是独读版 4-6 档、这次要共读版 6-8 档，落点重复一样要避。
  所以这一侧只守两条硬边界（owner 与形态），相似度交给打分。
- **`form` 两侧都要求"同形态或通配"**：拿独读版的落点去避共读版的重复是错的
  （共读版多一个选择点，落点分布不一样）。库里的样书是通配——它们是线性的，
  但作用只是"句子长什么样"，与形态无关（见 §三）。
- ★ **主题那三档形状，落地时才看清**（工单 04 追着数据流量的，见那个工单的 Comments）：
  请求里的 `theme` 有**三种**可能，而库里 chunk 存的是**键**：
  1. **键**（`'cloud'`）——脚本与内部调用；
  2. **中文名**（`'云'`）——**界面上走的就是这一种**（`create/page.tsx` 送 `THEMES[].label`）。
     不归一的话 `chunk.theme === 'cloud'` 与 `'云'` **永不相等**，这个过滤器在线上
     **一次都不会命中**，而症状是"检索永远没有范例"，不是报错；
  3. **家长那句话**——没点主题卡时 `state.ts` 的 `theme: form.theme.theme.trim() || wish`。
     这一档**不构成主题约束**（不是"主题不对"，是"这次没有主题"），所以不拿它去筛，
     而且它是**内容**：`queryTextOf` 会把它放进查询串。
     ★ 与「过滤不命中就是空集、不许兜底」不冲突：那条管**筛完之后**为空不许放宽，
     这里定的是**筛子本身在什么时候成立**。

**正反两面同一次检索出，且不重叠**（`retrieveBoth`）：

- **正例**：库 + 自己的旧书，取 top-3 → 注进提示词，给节奏与用词。
- **反例（负向检索）**：只取 `owner = 自家`、且分数高于阈值的 top-3 →
  明令「这些已经给他写过了，不要重复」。这是「再来一本还不重样」的技术落点，
  也是这一栏里最像**新东西**的一条。
- ★ **一条 chunk 不许同时出现在两栏里**：那会让提示词自相矛盾
  （"照着这个节奏写"与"不要重复这个"说的是同一个东西），而模型面对互相打架的两段话，
  行为是不确定的。这个不变式住在 `retrieveBoth` 里，调用方没机会做错。
- ★ **先算 `avoid` 再算 `example`**：反例是硬边界（"他读过了"不因为取几条而变化），
  正例是可替换的（少一条范例故事照样编得出来）。倒过来的话，一条刚要进反例的旧书
  会被正例先占住，"别重复"这件事就漏了。

★ 阈值与 k 都是**量出来的**，不是拍的：工单 06 的对照跑测同时扫
（k ∈ {1,3,5} × 阈值 ∈ {低,中}），把结果写进 `.out/rag-bakeoff/report.md`。
先给一组初值跑通，再由数据定稿——**改了要升 `PROMPT_VERSION`** 与语料指纹。


★ **一条硬红线，写进提示词也写进纪律**：
**范例只许参考节奏与用词，不许照抄句子。** 不说这一句，模型会把范例的句子

```ts
retrieval?: {
  corpusVersion: string           // ① 的指纹；② 每次现算，写 'live'
```

★ **可选**，理由与 `branchPages` 完全相同：2026-10-19 之前落盘的产物没有这个字段，
那是历史，**不重录**；读的时候没有就不显示。

**事件流**（`events.ts`）：

- `Stage` 加一档 `retrieving`，`STAGE_LABELS` 加「正在翻以前写过的故事」；

## 九、判据 4 第二轮（v2）预声明 —— **写于跑之前**（2026-10-19）

第一轮（v1）的口径是「Schema 一次通过率 **+10 个百分点** 或 平均重试 **−0.3**」。
两轮读数**变号**，并且查明了三条原因，全部有实测支撑：

1. **这个模型在格式上饱和**：两轮 60 次调用只 1 次重试，而那一次是**内容审核**拦下的
   （`R-01`），不是格式问题——v1 拿它当"生成质量"的代理，天花板本来就在 100%；
2. **n=10 时一本书就等于 10 个百分点**，而阈值正是 10 个百分点；
3. ★ **三分之一的样本剂量为零**：`--dryRun=1` 的预检行显示，两臂提示词的差是
   `382 / 287 / 439 / **0** / 91 / 283 / **0** / **0** / 281 / 180`——
   火箭、鲸鱼、城堡三个主题在 `minScore=2` 下**一条范例都取不到**，
   于是那三本两臂的提示词**逐字节相同**（"处理组"其实是对照组，占样本 30%）。
   根因是**主题这件结构化信号只当了过滤器、一分也不加**：同主题那本样书的跨页
   按"与家长那句话的字符重合"打分，落在 1.5–1.8，被阈值 2 挡在门外。

**所以 v2 换三件事，逐条定死，跑之前不许再改：**

1. **判据落点换到「内容量」**：v1 用一个饱和的代理量测"质量"。v2 的两个端点都落在
   文本本身，而且都是产品承诺的直接判据。
2. **主判据 `③`**：新书写出的句子里，含 **≥6 字连续子串**、且该子串出现在
   **同一主题那本旧书**里的句子占比（书级）。**该值 `lexical` 臂显著低于 `off` 臂**。
   —— 它测的是「再来一本还不重样」这件事，也就是负向检索的存在理由。
3. **副判据 `②`**：**超长句（>18 字）比例**，同上（`lexical` 显著低于 `off`）。
   辅助读数列（**不参与裁决**）：落在 12–18 字区间的句子比例、超纲字比例。
4. **显著性口径（事先定死）**：书级**配对**——同一主题的 R 次重复先取臂间差的
   **主题内均值**，得到 10 个配对观测，再做 **Wilcoxon 符号秩检验**（双侧）。
   **主判据要求 p < 0.025**（两个端点，压住族错误率）、**副判据 p < 0.05**；
   同时要求效应量 |Δ| **主判据 ≥ 5 个百分点**、**副判据 ≥ 3 个百分点**——
   免得出现"统计显著但没有用"。
5. **样本与设计**：**10 主题 × 每主题 3 次 = 30 本/臂**；②创作史由**本流水线自己产出的
   10 本**（每主题一本，`off` 臂生成）充当——"他读过了"因此是**真的**
   （手写的三本旧书落点根本不是模型会写的那些，这是 ③ 在 v1 里饱和为 0 的原因）。
6. **护栏**：`④ 与范例的句子重合率` 仍不得高于对照组 **+5 个百分点**（照抄污染）。
7. ★ **v1 的读数与结论原样留在报告里**，不覆盖、不重算。v2 是**新跑的一轮**，
   不是拿旧数据换算法重判——两轮的数字在报告里并排，各自标明用的是哪一版判据。

**同一轮里的策略改动（这一条也写在这里，因为它会影响结果）**：
阈值从"一刀切"改成**按池子的收窄程度分档**——池子被**主题**（`example`）或
**owner**（`avoid`）收窄过时用低阈值（1），没被收窄时（请求里认不出主题 → 整座库）
仍用 2。理由一句话：**阈值管的是"收窄之后剩下的精度"，池子已经被元数据收窄过，
阈值就不必再收窄一遍**；而"请求里认不出主题"那条路仍然是整座库，低阈值会把
不相关的范例喂进去（`retrieve.ts` 文件头警告过的那种坏法）。
读数上它把剂量从 **6/10 个主题取到范例**提到 **10/10**（扫描表在 `.out/rag-bakeoff/`）。

**v2 的读数（2026-10-19 跑完，填在这一节里）**

命令：`node scripts/rag-bakeoff.mts --books=10 --repeats=3 --cells=3:2:2 --out=.out/rag-gain-v2`
（10 主题 × 每主题 3 次 × 3 臂 + Phase 0 造 ②创作史）。**60/60 全部测成**，限流 0、调用失败 0，
成本 114 次文本调用。报告：`.out/rag-gain-v2/report.md`。

| 端点（配对，精确符号秩） | `off` | `lexical` | 差                | p    | 门槛           | 判       |
| ------------------------ | ----- | --------- | ----------------- | ---- | -------------- | -------- |
| `③` 与本主题旧书的重复度 | 3.3%  | 3.8%      | **+0.5 个百分点** | 0.81 | ≥5pp · p<0.025 | **不过** |
| `②` 超长句（>18 字）比例 | 6.1%  | 5.8%      | **−0.3 个百分点** | 1.00 | ≥3pp · p<0.05  | **不过** |

- **功效**（事后算的，只用来解释"为什么测不出"，**不参与裁决**）：`③` 的最小可检测效应

  观测到的差是 **1 个百分点上下**——**与设计能看见的量级差了一个数量级**。
  所以"不显著"在这里不是"差一点"，而是**远在可检测范围之下**。
- ★ **我们的口径错了一处，记在这里不悄悄改**：`③` 的效应量门槛 ≥5 个百分点，
  而对照组基线只有 **3.3 个百分点**——**重复度不可能低于 0，那道门槛数学上就达不到**。
  门槛是量出基线之前拍的。**下一个想测"不重样"的人：先量基线，再定门槛。**
- ★ 但 `③` 这条端点在 v2 里**第一次活了**：v1 用它测手写旧书，两臂都是 0.0%（饱和）；
  v2 把 ②创作史换成本流水线产出的 10 本之后，`off` 臂基线变成 **3.3%**（个别主题 16.7%）。
  **量具修好了，只是 treatment 的效果没被量出来。**
- **策略改动生效了**（这一条与判据无关，但它自己的读数很清楚）：预检行从
  `382 / 287 / 439 / 0 / 91 / 283 / 0 / 0 / 281 / 180` 变成**十个主题全非零**
  （`382/188/395/373/183/383/193/377/281/180`）——**剂量为零的样本从 30% 降到 0**。
- **方向性读数（★ 探索性，不是判据）**：落在 12–18 字区间的句子比例 45.5% → 50.3%（p=0.63）；
  `④` 与范例的句子重合率 0.3% → 1.0%（**仍远低于**对照组 +5 个百分点，**没有照抄污染**）；
  **内容审核命中 4/30 → 0/30**（`off` 臂那 4 次重试全部来自内容红线 `R-01`，
  两条开了检索的臂一次都没有）——方向一致、机制讲得通，但**没预注册、也不显著**，

  所以**不能说"更适龄"**，只能说方向一致、幅度不稳。
- **④ 与范例的句子重合率 0.0% / 0.0%（两轮三臂全 0）**——这一层**没有把书变坏**，
  范例那条红线（"只许参考节奏，不许照抄句子"）守住了。这是这一轮最硬的一条。
- ③ 与 ⑤ **饱和**（对照组本来就 0 重复 / 100% 新意）：测不出差异，不是"没用"。
