## 为什么这一条能与检索共用一件东西

`plan.ts` 只把红线写在**提示词**里：模型真写出一段吓人的东西，**没有任何代码拦得住它**，
而这段东西会直接念给一个 4 岁的孩子听。`.scratch/w1-engine/issues/06` 自己点名过：
「审核 Agent 的红线词库还没有，只有 prompt 里那三行」。
`events.ts` 里 `review` 那个事件与 `auditing` 那一档**早就留好了座位**，从未 emit 过。

★ 它和规划那条**共用同一个检索器**，但用法不同——这一点必须说清，否则会被做成检索的壳：

| 层                       | 怎么跑                                                      | 为什么                                                                                               |
| ------------------------ | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **硬规则层**（每次全跑） | 词表 / 字表**确定性扫描** `body` 与家长那句自由输入         | 这是规则不是检索。拿向量去「检索」一条你知道一定要用的规则是糊弄                                     |
| **条款检索层**（取子集） | 拿**这一页的文本**检索出**适用**的语义型条款，交 LLM 逐条判 | 语义型条款（「情绪必须被故事接住」「不许说教」）词表扫不出来；而条款会长到几十上百条，每次全塞是噪声 |

## 要做的

```
node scripts/review-cases.mts

正例：10 条里 9 条该拦、1 条预期漏过（漏过 1 条是词表的已知盲区，不是回归）
反例：12 本样书 96 个跨页 + stub 那一版 demo 故事 → 误拦 0 条（一条都没有）
✓ 过了：该拦的全拦下，真人写过的文本一条都没误拦
```

九条拦下的都**报出了条款 id**（`R-01`…`R-06`），没有一条是「生成失败」。第十条是
**死亡 · 委婉说法**（「小狗睡着了，再也没有醒过来」）——它按计划漏过，
报告里记成 `漏过（预期）` + 缺口说明，**留在用例表里**（本张验收就要求这样）。
它哪天被拦下了，脚本会报成「★ 与预期不符」，那才是语义档落地的信号。

**一处对工单的偏离，如实记：`unavailable` 没用上，改用 `unchecked`**

工单验收里那句是「`unavailable`（模型判不了）时**不是 pass**」。实现下来发现它**不成立**：
`unavailable` 要有一个**会跑、会失败**的比较器（一致性核对那边就是），
而语义档那三条（说教 / 情绪接住 / 适龄）**今天根本不存在**——不是"跑了但判不了"。
把它们摊成一个 `unavailable` 状态，会让**每一本书**都挂着"未审核"，
而它并不会更安全，只会让那个词失去意义。

所以改成：`reviewStory` 返回里多一个 `unchecked: string[]`（那三条的 id），
`verdict` 照常算。★ 它是一条**如实的记录**而不是一个状态：调用方说得出来"今天只审了词表这一档"，
但它不参与裁决。理由写在 `review.ts` 文件头第三节。

**闸门的位置比起工单往前挪了一格：出图**之前**，不是装订前**

工单写的是「`illustrate.ts` 那一侧在装订前跑一遍审核」。落地时放在 `illustrateBook`
**最前面**（第一张图都还没画）。理由是钱：出图是这条流水线上唯一真花钱的一步，
而「装订前」那一版拦下来的，图**已经画完了**。
反过来（放在最前）是严格更好的位置，没有任何代价。

于是有两道闸，不是一道：

| 在哪              | 什么时候跑                   | 拦不住的会是谁                                     |
| ----------------- | ---------------------------- | -------------------------------------------------- |
| `plan.ts`（规划） | `plan-ready` **之前**        | 模型当场写出来的那一版                             |
| `illustrateBook`  | **第一次 provider 调用之前** | **家长在故事闸门上改出来的那一版**（`story.json`） |

第二道不是重复：家长逐字改过的正文不经过规划那一步，而它才是接下来要画、要念的东西。
只留第一道的话，家长手打进去的每个字都绕过了闸门。

★ 第二道上 **`flag` 也拒发**（与第一道不同）：那里没有"重写一版"这条路——
`illustrateBook` 不重做规划（会丢掉家长改的东西，还再花一次文本调用）。
事件里的 `verdict` 仍如实报 `flag` / `block`，让界面说得清是哪一种。这条写在 `index.ts` 那段注释里。

**★ 写反例时，自己的词表先咬了一口：`点着` → `点燃`**

`R-06` 原来收 `点着`（意思是"点着火"）。写完 `review.test.ts` 里那棵共读版的树，
它当场把**「花在风里点着头」**拦成了危险示范——`disposition: block`，也就是"这一版不能给孩子看"。

- 它没被 96 段样书抓到：样书只有 `caption` + 正文，**没有 `scene` / `imagePrompt` / 选择点**，
  而"点头"不出现在正文那一层。所以反例集补了 `scripts/fixtures/demo-plan.json`
  （stub 那一版 demo 故事，有人写的 `scene` 与 `imagePrompt`）。
- 处置：换成 `点燃`。判据是它在这个题材里没有第二种常见意思。
- 这就是 `review-corpus.ts` 文件头第三节那条判断（"能收双字词就收双字"）**第二次**付学费，
  所以它的验证方式写在那里的是"拿真文本跑一遍"，不是"我觉得"。

**顺手改掉的一句屏幕文案**

`describeEvent` 的 `review` 分支原来直接印枚举值（屏幕上会长出「内容检查：flag」）。
它错得起，是因为这条分支**从未被走到过**。闸门接上之后它第一次会上屏幕，所以一并改成四句人话；
`reason` 有值就原样用它（`reviewProblemText` 给的是一整句，带页码、条款 id 与命中的词），
加前缀会变成"同一件事说两遍"。

**今天明确没做的三件（都不是遗漏，是不做）**

1. **适龄字表**：`R-09` 是 `semantic`，文件头里写着"今天没有机械判据"。
   `AGE_RULES` 是散文，把它变成字表要一次真跑测（哪一档的用词长什么样），不属于本张。
2. **语义档**（说教 / 情绪接住 / 适龄）：要模型读，而它**不能当判据**——
   判据 5 的两个数（10 拦 / 0 误拦）必须天天一样。它们的 id 进 `unchecked`，进语料，不进裁决。
3. **画面审核**：图不是文字，词表扫不到；它该落在出图那一次调用之后（顺带问第二个问题），
   而不是 `review.ts`（那里是纯函数，不认识图）。写在 `review.ts` 文件头第五节，
   免得下一个人以为审过了。

**判据之外的两个数（只有真跑才分得出来）**

`scripts/review-cases.mts` 逐条比对了**处置与调用次数**：`block` 那三条（自伤 / 危险示范）

而是"引擎真的按处置走了"——让模型看着那段内容再改一遍，本身是一次多余的接触。
