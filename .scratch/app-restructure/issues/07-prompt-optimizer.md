# 07 · 提示词优化：用户点一下，把那句想法变成能开工的 prompt

Status: done
依赖：无（独立小功能，随时可插）
对应 Request 5：用户有时候描述的故事不是很好，系统应该提供一个优化提示词的功能

## 一、它优化的是哪个字段（先把范围钉死）

创作流第 2 步有两个输入（`state.ts`）：

| 字段          | 内容                                 | 优化吗                                  |
| ------------- | ------------------------------------ | --------------------------------------- |
| `theme.theme` | 从既有主题里**挑**的一个（`THEMES`） | ❌ 不优化，它是枚举值，改了就不是模板了 |
| `theme.wish`  | 用户**自己写的一句话**（"想讲什么"） | ✅ **就优化它**                         |

★ 这一条钉死很重要：如果优化按钮出现在主题那一行，用户会以为"挑了恐龙再优化"
会变成另一只恐龙——**按钮要长在它真正作用的那个输入框旁边**，长了别处就是误导。

## 二、它做什么

一次服务端 LLM 调用（用用户自己的 Env，ADR-0008 不变）：

```
输入：userWish（可能很短、可能很含糊）+ 孩子的名字/年龄档/兴趣标签（角色卡里已有）
输出：一条**更具体**的 wish —— 有场景、有冲突、有情绪落点，仍然是一句话
```

要求：

1. **不许替用户做决定**：优化后的句子必须回答"谁、在哪、遇到什么、最后怎么样"，
   但**不许**引入用户没提的、有争议的东西（死亡、走失、二胎、怪物吓人这些要避开——
   这是给 4–6 岁孩子的书）
2. **不许改变用户的意图**：如果用户写"想让孩子学会分享"，优化后不能变成"冒险故事"
3. **要能对比**：界面上是"你的版本 / 优化后"并排或上下，**保留原句**，
   用户点"用这个"才替换。★ 直接覆盖原句是这一单最容易犯的错
4. **失败就说失败**：调不通时显示人话（沿用既有错误文案的做法），
   **不要**在本地写一个"兜底模板句子"顶上——那会让用户以为 AI 优化过，
   而他拿到的其实是一句写死的话
5. 长度上限（比如 ≤ 80 字）和**适龄**检查（4–6 岁），超了要提示

## 三、实现落点

- 服务端：新增一条 Route Handler（沿 `src/app/api/cards`、`/api/books` 的先例）
- prompt 本体：放 `src/lib/prompts/`（已有 `story-plan.ts` / `image.ts` 的先例），
  **不在组件里拼字符串**
- 引擎侧复用：这是**文本生成**，复用 `TextGenerator` 的实现（`createProviders` 给的那条），
  **不新写一个 provider**。若发现现行 `TextGenerator` 接口喂不进这个用法，
  先在本单 Comments 里记下"接口不够用在哪"，再决定改接口——**不许**顺手为它新开一条通路
- 界面上是一个按钮 + 一块对比区，**不是**自动触发：
  用户写字的当下不要打断他（打字时自动优化 = 最烦人的那种 AI）

## 四、能被测的部分

prompt 的**输出**不可测（LLM），但下面这些可测：

- 请求体组装（wish 为空时按钮禁用 / 不出现）
- 原句在替换前后**一直在 `state` 里**（点"用原句"能回去）
- 失败路径：env 不全 / 超时 → 人话错误，且 `state.theme.wish` **未被改动**
- 长度与适龄校验的边界

★ 别为 LLM 的输出写断言。那是把"测过"变成一个假的数——**没测成不许记成测出来**。

## Comments

### 一、接口不够用在哪（§三 要求先记下来再决定改不改）

**结论：现行 `TextGenerator` 确实喂不进这个用法，加了一个字段，没有新开通路。**

`.env.local` 里 `LLM_JSON_MODE=object`，于是 `openai-text.ts` 对**每一次**文本调用
无条件带 `response_format: {type:'json_object'}`。而真实网关是 LiteLLM，它要求
messages 里出现 "json" 这个词。这条纯文本调用第一次真跑就 400：

```
/chat/completions 失败 HTTP 400 · LITELLM_ERROR ·
'messages' must contain the word 'json' in some form, to use 'response_format' of type 'json_object'.
```

★ **这个错是桩服务器照不出来的**：我先用一个本地桩把界面全验了一遍（全绿），
再拿真 key 跑探针才炸——桩把 `response_format` 当不认识就忽略了。
"界面验过了"和"这条路能跑"是两件事。

**改法**（`TextRequest.plainText?: boolean`，默认 `false`）：

- 默认值下**现有每一条路逐字节不变**——规划、审核、视觉判定照旧受 `LLM_JSON_MODE` 管。
  这一点是硬要求：W1 横评的数字是在 `object` 档下量的。
- 提示词里塞一个 "json" 能骗过这道检查，**没这么做**：那是为了让一个不该来的参数过关
  而往提示词里写一个与任务无关的词，换一家网关就得再猜一次。
- `optimizeRequest()` 把**整份**请求（含这个字段）收在一处，路由与探针都调它——
  探针自己拼的话，漏掉的正好是最容易漏的那个字段。

### 四、界面（浏览器实测，逐条）

用本地桩把界面全跑了一遍（桩值 **不是**生产配置，因为 key 按 ADR-0008 只活在内存里，
不可能也不该把它填进浏览器）：

| 验的                                                  | 结果                                                                                                  |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 优化后**原句还在框里**（§二 第 3 条那件最容易犯的错） | ✅ 建议出现时 `textarea` 值不变，原句逐字保留                                                         |
| 「用这句」                                            | ✅ 替换成建议那一句，按钮变成「退回原句」                                                             |
| 「退回原句」                                          | ✅ 退回的是**提出建议时框里那一句**，逐字相同                                                         |
| 「不用」                                              | ✅ 建议消失，框里的字一个字没动                                                                       |
| 原句被改过之后                                        | ✅ 出来一句"你后来改过原句了，这一版是照着改之前那句写的"（不静默清掉，也不让他拿对不上的一句去替换） |
| 正在飞的时候                                          | ✅ 按钮变「正在想…」且禁用；建议区不显示半截结果                                                      |
| **连点三下**                                          | ✅ 桩只收到 **1 个**请求                                                                              |
| 缺文本密钥                                            | ✅ 不报错，直接把设置打开                                                                             |
| 故意填错 key（真地址 + 假 key）                       | ✅ 人话 + 可排障原文，`wish` 未改                                                                     |
| 端口没人听                                            | ✅ 出错误、`wish` 未改、建议未被替换、按钮恢复可用                                                    |

★ **连点那条是实测抓出来的 bug**：第一版守卫写的是 `if (thinking) return`（state），
桩收到 `SLOW-REQ#1`、`SLOW-REQ#2` 两条——React 重渲染是异步排的，同一帧里第二次点击
读到的还是旧的 `thinking`。改成 ref 之后重测：连点三下 → 1 个请求。
`disabled` 属性拦不住同帧的第二下，它同样要等重渲染。

### 五、没做 / 不能做的，说清楚

- **超长的建议不截断**，只显示一句"长了一点"。截一半的句子看起来像模型没写完，
  比长句子坏得多。到目前 14 条没出现超长，所以这条提示**没有被真实触发过**——
  它是按 §二 第 5 条要求写的，实测里没走到。
- **"关掉网络"那条我测的是"端口没人听"**（`fetch failed`），显示的是
  `没改成：/chat/completions 网络错误：TypeError: fetch failed`。**这不是人话**，
  是 `engine/providers/http.ts:184` 直接把 `String(err)` 拼进去的结果，
  而 `userFailureOf` 对"没有状态码的网络错"是原样透传。**这是共用层的既有行为，
  影响 `/api/cards`、`/api/books`、设置里那几个"试一试"**，不只这一条路——
  所以**没有**在这一单里顺手改它（改一处会同时改掉所有路线的文案，
  那是另一次单独的改动）。★ 这一条是**已知缺口**，不是已修项。
- **没做自动触发**（§三 要求）：打字时不优化，只在点按钮时发一次。
- **没在本轮做**：把优化结果记进 `Provenance`。它改的是**输入**、不是产物，
  现在版本号只用于排障。哪天要做"这本书的那句话是被优化过的"，再说。
