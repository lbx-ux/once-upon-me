## 一、为什么"抽出来"是对的（不只是界面整洁）

现在这两步埋在创作流里，代价是**每次做书都要重填一遍孩子**。而
[ADR-0007](../../docs/adr/0007-character-card-as-asset.md) 早就把角色卡定义成
**内容寻址的资产**、`store.ts` 也已经建好了 `cards/<cardId>/r1.… r2.… latest` 的目录形状
——**资产的含义就是可以跨书复用**。所以这次抽离不是新架构，是把 ADR-0007 已经
承诺过、而界面没兑现的那句话兑现掉。

推论（会影响 [04](04-settings-drawer.md) 与 [05](05-home-dashboard.md)）：

- 创作流第 1 步从"填孩子"变成"**选一个已有角色**，或新建一个"
- 主页"我的故事"旁边会自然长出"我的角色"
- 删一个孩子 = 删掉他所有版本的角色卡 + 原图 + 他的书（`deleteChild` 已有，要接出来）

## 二、三块屏幕

### 2.1 `/characters` —— 角色列表

- 两张**示例角色**卡在最前面：小宇（男孩）、小满（女孩）——资产来源见 [spec §二·五](../spec.md)
- 自己的角色按最近使用排序
- 空态（新用户，一个自己的角色都没建过）：**不许**写成"还没有角色哦～"这种空话，
  要写成"这里会放你孩子的角色卡。可以先用上面两个示例角色做一本书看看效果。"
- 每张卡露出一张形象图 + 名字 + 年龄档 + "第 N 版"

### 2.2 `/characters/new` —— 新建：照片 + 特征 + 名字 + 年龄

**两个入口，默认是第一个**（与 [spec §二之补](../spec.md) 的答辩口径一致）：

| 入口                           | 行为                                                           |
| ------------------------------ | -------------------------------------------------------------- |
| **从零描述**（默认，无需照片） | 沿用现有锚点表单 → 出 1 张形象。这条路**不进任何未成年人图像** |
| **上传照片**（需要单独同意）   | 照片 + 特征 + 名字 + 年龄 → 出 1 张插画形象                    |

上传那一路的界面要求：

- 同意是**一次勾选 + 一段可读的说明**，不是一行灰字
- 说明里写死三件事：只用于生成这本书的插画 / 处理完即删 / 不用于训练
- 上传后**显示我们做了什么**（"已压平到白底、缩到 1440²"），因为
  [02](02-reference-image-pipeline.md) 的归一化会改这张图
- 拒绝也要给人话：小于 240px 时写"这张照片太小了，至少要 240×240"

必填项沿用 `stepProblems` 的判据（**同源**，不许界面自己重写一遍校验）：
名字、名字读音、年龄档。★ 读音必填的理由在 `state.ts` 里写着——"多音字读错是家长
第一秒就能发现的错"。

### 2.3 `/characters/[childId]` —— 形象页：看、提建议、再画一版

这是 Request 3(a) 里最新的一条：**"根据刚才生成的插画进行建议"**。
机制是现成的 revision（见 [spec §二·五 ②](../spec.md)），新的是输入方式：

```
[ 形象图 v2 ]   ← 默认显示 latest
"想改哪里？"  [ 眼睛再大一点，头发短一些          ]  [ 再画一版 ]
```

- 提建议 → 走 [02](02-reference-image-pipeline.md) 的 `edits`：**参考图 = 上一版插画**，
  prompt = 那句建议 + 角色卡的锚点段
- 每次产出 = **新 revision**，旧版**必须留着**（`store.ts` 文件头第 1 条理由：
  "旧书的那些页出自旧版，覆盖了它们，'这张图是哪版角色卡画的'就答不上来"）
- 界面上要能看到版本历史，并能切回旧版（切回 = 改 `latest` 指针，不是删新图）
- ★ 建议的输入框旁**不许**写"AI 会尽力理解"这类免责话。它要么能改，要么就明说
  这条建议没被采纳——两边都由 [02](02-reference-image-pipeline.md) 的
  **锚点核对**环节来判断。`make-demo-cards.mts` 已经示范过这个模式：
  "锚点先写进 prompt，再由同一批锚点去核对"，核对结果**打印出来**，不通过就重画。

### 2.4 一致性怎么判（★ 不许用 `r_redraw`）

工单 [w2-06] 与 [spec §四 未决 4](../spec.md) 都记着：**一致性比对器的阈值没重校准，
`r_redraw` 不能用**。所以本单所有"像不像"只报两样东西：

- 锚点核对**逐条的 pass/fail**（视觉模型做的，已经有实现）
- 与上一版/照片的**原始分数**，且**不给用户看**、不进界面文案、不进汇报

## 三、隐私：这一单是风险最大的一单

| 项       | 要求                                                                                      |
| -------- | ----------------------------------------------------------------------------------------- |
| 照片原图 | 生成后**不留**（`store.ts` 只存 `ref.<digest>.webp`，那是**产物**不是原图；原图不许落盘） |
| 删除     | `deleteChild` 接出来，且**要报数**（隐私设计 §九 的删除凭据：                             |

       "每个存储位置各删了多少条"）。上传的原图也要被数进去，哪怕它不落盘——数的是"处理过" |

| 录进事件流 | 照片**不许**进 `events.jsonl`（那是可重放的文件，会带上 base64 或路径） |
| 进日志 | ★ 沿用既有纪律：**不进日志、不进录制 manifest**。要有一条测试或 `grep` 证据 |
| 默认 | 合成角色是默认路径；照片是家长主动开的第二条路 |

**★ 两个 bug 是"在浏览器里点了一遍"才发现的，静态读代码都看不出来。**
共同点是：**在某个动作出现之前，错的那一版与对的那一版永远一致**。

1. `summaries()` 拿"扫目录取 revision 最大"当"当前版"。切回第 1 版之后，`latest`
   文件里明明写着 `1`，列表页还说第 2 版是当前。现在必须走 `load()`（它读那个指针），
   指针指不到东西时才退回最大 revision。用例写在 `store.test.ts` 的 `summaries` 那一组，
   组名的注释里写着它是怎么被发现的。
2. 形象页"从现在起用这一版"那颗按钮的条件是 `shown.revision > 1`，于是
   **切回第 1 版**——最常发生的那一次——根本没有按钮。判据只有一条：
   看的那一版**不是**现在在用的那一版。（同样由点击发现，注释留在 `ChildDetail.tsx`）

**这一刀刻意没做的判断**（每条都有具体理由，不是偷懒）：

- **不自动判"这条建议被采纳了吗"**。现有比对器问的是"图上有没有这几条锚点"，
  而这次动的正是锚点管的那些部位——"眼睛再大一点"会让"深棕色圆眼"判**不**像，
  于是**成功会被判成失败**。要自动判得先有"两张图 + 一句判据"这个新的比对形态。
  在那之前，**新旧两版并排给家长看**就是判据，而且它不需要免责话。
- **切回旧版不叫"撤销"、不二次确认**：它只动那个一字节的指针，不删任何一版。
- **`validateCard` 有和 `validateProfile` 一样的隐患**（对形状不对的输入不总收）。
  没顺手改：它属于建卡那条路，改了要连带动 02 的验收。

**★ 这一刀真正的收获是两个 bug，两个都是在"真跑 + 核查磁盘"里露出来的：**

1. **缩略图与卡片平级，删卡不删图。** `thumbs/<档>/cards/<cardId>/…` 在 `cards/` 之外，

   这不是推理出来的：开工前资产根里躺着 **9 个这样的残留**，全是我自己在前面几刀里

2. **`deletePrefix` 的两个实现对"前缀落在一个文件上"回不一样的数**：内存版按键前缀

### 四、★ 验证时发现并修掉的一个真缺陷（不是这次新写的，是两处改动撞出来的）

闭环探针（见下）跑出来的第一版结果里有这么一行：`mark:（没读到）`。
链起来看是这样：

1. 读照片这条路会**刻意清空**模型看不见的槽位（上面那条理由）；
2. 而本刀同一天给 `checkAnchors` 加了一条「空值也算问题」（补的是另一个会花钱的漏洞）；
3. `特征记号` 与 `常服` 是**软锚点**——`REQUIRED_SLOTS` 里没有它们，
   `normalizeAnchors` 丢掉它们之后卡照样合法。

三件事各自都对，合起来是：**家长读完一张照片，看到「记号是空的」，按钮点不动，
而那张卡本来完全合法**。而"照片里看不见记号/常服"是这条路上的常事
（这次实测的输入图就看不见）。

修法是**把"空值算错"限定在硬锚点**——判据一句话概括是
「**空值只在'缺了它会出不了图'的槽位上算错**」，因为上面那段"界面比服务端松"的
推理在软锚点上不花任何钱。改动在 `checkAnchors`（`card.ts`），配两条用例：
软锚点空着**不算**问题、硬锚点空着**仍然**算问题（不许把花钱那道缝一起放开）。

★ 值得记的是**它是怎么被发现的**：不是读代码读出来的，是**看探针的输出**
（那一行"没读到"）想起来"那界面会报什么"。所以探针要把**原始产物**打出来，
只打一个"通过/不通过"会漏掉这一类。

### 三、★ 我上一版那条断点是错的（这一刀实测抓出来的）

上一刀我写的两列断点是 `@media (min-width: 1100px)`，推导是按

错的后果不是"不够漂亮"，是**每一格都放不下值**：

| 视口 | 右栏实测 | 两列每格 | 七条示例值                   |
| ---- | -------- | -------- | ---------------------------- |
| 1100 | **349**  | **163**  | 溢出 24–98px，**七条全被切** |
| 1440 | 665      | 321      | 一条都不切                   |

判据本来就是"这一栏有多宽"，所以改成让它**量自己那一栏**：
`.nc__anchors { container-type: inline-size }` + `@container (min-width: 500px)`。

**阈值 500 的来路**（复现：`.out/probe-nc-width.mjs` 打印每格的 `scrollWidth − clientWidth`）：
最长的**非**常服示例值是「黑发偏软，左侧总有一撮翘起来」210px，加输入框左右内边距 24
→ 每格 ≥234；两列再加 24 的栏间距 → 容器 ≥492，取 500。低于它宁可长、不可挤
（与 `.cf__pair` 窄屏落回一列是同一条判断）。
★ 常服在 245px 的格子里仍差 16px（它的值是"一整套衣服"，235px），所以让它独占一行——
按位置选它是因为 `ANCHOR_SLOTS` 声明序里它就是最后一条；往槽位里加东西时先回来看一眼。

★ 值得记的是**两条错误都是"我以为的数"**：一条是算漏了侧栏，一条是探针第一个数块
标签写着 1440、量的其实是启动时那个 1280（已修）。两个都不会报错，只会让结论偏。

### 一、第八格为什么是「软」锚点、为什么排在**最后**（两个决定都是为了不弄坏磁盘上已有的东西）

1. **软，不是硬。** `checkAnchors` 只对**硬**槽位报空错（`REQUIRED_SLOTS` = hard only）。
   如果把补充做成硬锚点，**磁盘上每一张已有的卡**（七格，没有 `extra`）在 `validateCard`
   那一刻全部变成不合法——家长打开旧角色卡就得到一句"锚点不完整"，而卡上一个字都没改过。
   软锚点空着本来就合法，旧卡原样通过。语义上也对：补充是"还可以再说一句"，不是"必须说一句"。
2. **追加在末尾，不插在中间。** `ANCHOR_SLOTS` 的顺序不是排版顺序，是**提示词顺序与指纹顺序**：
   `normalizeAnchors` 按声明序排（`card.ts:145` 那句"排序是指纹稳定的前提"）、
   `promptFragmentOf` 按声明序拼、`cardDigest` 吃的就是排好的锚点数组（`card.ts:254`）。
   插在中间会让**每一张已有卡的指纹变**——内容没变、指纹变了，于是文件名里那个
   `ref.<指纹>.webp` 全部对不上，参考图一夜之间"丢了"。追加在末尾，旧指纹一个字节不变。

### 一、先回答"为什么"：**和照片清不清楚无关**

用户那句「照片信息已经很清晰了」是合理推断，但它指错了地方——这句报错发生在**模型读完
之后**，而排障原文那个括号里是**空的**。空括号说明 `content` 是空串：模型这一趟**什么都没写**。
照片清晰度决定的是"读到的东西准不准"，而这一次是"它根本没交卷"。

★ 我**没能复现**（这一点必须先说清）：真打 `kimi-k2.6` 五次（`.out/vision-raw-2.log` …
`-5.log`）五次都成功。所以下面这些不是"猜的原因"，是**从回包里读出来的机制**：

```
顶层键：id, created, model, object, choices, usage, cost_cny, billing_pending, trace_id
message 的键：content, role, reasoning_content, provider_specific_fields
finish_reason：stop
usage：completion_tokens 2526 · prompt_tokens 3094 · reasoning_tokens 2395
```

它是**推理模型**：一次读照片要产 2400+ token 的思考链，而正文只有 250 字上下。
"想完了没写"、"正文被上游截掉"都是这种模型**偶发**的坏法，而它偶发到什么程度——
五次里一次都没轮到（用户那次轮到了）。

### 二、真正确定的是**我们这一侧的两个缺陷**（都不依赖复现）

| #   | 缺陷                                  | 症状                                                                                                        | 改法                                                                                                                         |
| --- | ------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 1   | 读回包只认 `message.content` 一个字段 | 正文空时排障原文**是空的**，界面上那句"（原文前 120 字：）"没有下文；思考链明明有 4000 字，我们一个字都不看 | `readReply()` 一起捞 `content` / `reasoning_content` / `finish_reason` / `refusal`，失败时带上**思考链的末尾**               |
| 2   | 重试推给家长                          | 界面上写着"再点一次通常就好了"——等于让用户手动重试                                                          | 引擎自己试第二次（**只针对"拿到回包但内容不能用"**；`requestJson` 那条"4xx 不重试"不越过），界面改成如实说"已经替你试过两次" |

★ 第 1 条还顺手补了一个**静默**的洞：`content` 除了字符串还有**分片数组**形状

### 二、这一刀真正有风险的一处：`{demoId ? null : …}` 把两件事的判据合并了

原来那一节是**人人都渲染**，示例孩子只是在里面换一句话。改成整节按 `demoId` 决定之后：

1. **示例孩子再也看不到"为什么删不掉"**——这是有意的（见上表），但代价是诚实的：
   屏幕上除了那颗不存在的按钮之外，不再有任何地方说明"示例角色删不掉"。
   服务端那道门一个字没松（下面 ② 组就是钉这个的）。
2. **一种边缘档案会多出一个坏链接**：本机手工把示例 id 覆盖成自己的档案时
   （`source` 是 `local`、`demoId` 仍为 `true`），角色卡上那颗「删掉他」
   （`CharacterWall.tsx:258`，无条件渲染）链到 `/character/<id>#delete`，
   而 `#delete` 那个落点**已经不在了**，点过去只是滚到页尾。
   这段代价写在 `ChildDetail.tsx` 那一节上面的 ★ 注释里（518 行附近）。
   判断是**值得**：那种档案只在本机手工造过才存在，而它真去删仍会被服务端 403 挡下。
