## 一、为什么"抽出来"是对的（不只是界面整洁）

现在这两步埋在创作流里，代价是**每次做书都要重填一遍孩子**。而
[ADR-0007](../../docs/adr/0007-character-card-as-asset.md) 早就把角色卡定义成
**内容寻址的资产**、`store.ts` 也已经建好了 `cards/<cardId>/r1.… r2.… latest` 的目录形状
——**资产的含义就是可以跨书复用**。所以这次抽离不是新架构，是把 ADR-0007 已经
承诺过、而界面没兑现的那句话兑现掉。

推论（会影响 [04](04-settings-drawer.md) 与 [05](05-home-dashboard.md)）：

- 创作流第 1 步从"填孩子"变成"**选一个已有角色**，或新建一个"
- 主页"我的故事"旁边会自然长出"我的角色"
- 删一个孩子 = 删掉他所有版本的角色卡 + 原图 + 他的书（`deleteChild` 已有，要接出来）

## 二、三块屏幕

### 2.1 `/characters` —— 角色列表

- 两张**示例角色**卡在最前面：小宇（男孩）、小满（女孩）——资产来源见 [spec §二·五](../spec.md)
- 自己的角色按最近使用排序
- 空态（新用户，一个自己的角色都没建过）：**不许**写成"还没有角色哦～"这种空话，
  要写成"这里会放你孩子的角色卡。可以先用上面两个示例角色做一本书看看效果。"
- 每张卡露出一张形象图 + 名字 + 年龄档 + "第 N 版"

### 2.2 `/characters/new` —— 新建：照片 + 特征 + 名字 + 年龄

**两个入口，默认是第一个**（与 [spec §二之补](../spec.md) 的答辩口径一致）：

| 入口                           | 行为                                                           |
| ------------------------------ | -------------------------------------------------------------- |
| **从零描述**（默认，无需照片） | 沿用现有锚点表单 → 出 1 张形象。这条路**不进任何未成年人图像** |
| **上传照片**（需要单独同意）   | 照片 + 特征 + 名字 + 年龄 → 出 1 张插画形象                    |

上传那一路的界面要求：

- 同意是**一次勾选 + 一段可读的说明**，不是一行灰字
- 说明里写死三件事：只用于生成这本书的插画 / 处理完即删 / 不用于训练
- 上传后**显示我们做了什么**（"已压平到白底、缩到 1440²"），因为
  [02](02-reference-image-pipeline.md) 的归一化会改这张图
- 拒绝也要给人话：小于 240px 时写"这张照片太小了，至少要 240×240"

必填项沿用 `stepProblems` 的判据（**同源**，不许界面自己重写一遍校验）：
名字、名字读音、年龄档。★ 读音必填的理由在 `state.ts` 里写着——"多音字读错是家长
第一秒就能发现的错"。

### 2.3 `/characters/[childId]` —— 形象页：看、提建议、再画一版

这是 Request 3(a) 里最新的一条：**"根据刚才生成的插画进行建议"**。
机制是现成的 revision（见 [spec §二·五 ②](../spec.md)），新的是输入方式：

```
[ 形象图 v2 ]   ← 默认显示 latest
"想改哪里？"  [ 眼睛再大一点，头发短一些          ]  [ 再画一版 ]
```

- 提建议 → 走 [02](02-reference-image-pipeline.md) 的 `edits`：**参考图 = 上一版插画**，
  prompt = 那句建议 + 角色卡的锚点段
- 每次产出 = **新 revision**，旧版**必须留着**（`store.ts` 文件头第 1 条理由：
  "旧书的那些页出自旧版，覆盖了它们，'这张图是哪版角色卡画的'就答不上来"）
- 界面上要能看到版本历史，并能切回旧版（切回 = 改 `latest` 指针，不是删新图）
- ★ 建议的输入框旁**不许**写"AI 会尽力理解"这类免责话。它要么能改，要么就明说
  这条建议没被采纳——两边都由 [02](02-reference-image-pipeline.md) 的
  **锚点核对**环节来判断。`make-demo-cards.mts` 已经示范过这个模式：
  "锚点先写进 prompt，再由同一批锚点去核对"，核对结果**打印出来**，不通过就重画。

### 2.4 一致性怎么判（★ 不许用 `r_redraw`）

工单 [w2-06] 与 [spec §四 未决 4](../spec.md) 都记着：**一致性比对器的阈值没重校准，
`r_redraw` 不能用**。所以本单所有"像不像"只报两样东西：

- 锚点核对**逐条的 pass/fail**（视觉模型做的，已经有实现）
- 与上一版/照片的**原始分数**，且**不给用户看**、不进界面文案、不进汇报

## 三、隐私：这一单是风险最大的一单

| 项       | 要求                                                                                      |
| -------- | ----------------------------------------------------------------------------------------- |
| 照片原图 | 生成后**不留**（`store.ts` 只存 `ref.<digest>.webp`，那是**产物**不是原图；原图不许落盘） |
| 删除     | `deleteChild` 接出来，且**要报数**（隐私设计 §九 的删除凭据：                             |

       "每个存储位置各删了多少条"）。上传的原图也要被数进去，哪怕它不落盘——数的是"处理过" |

| 录进事件流 | 照片**不许**进 `events.jsonl`（那是可重放的文件，会带上 base64 或路径） |
| 进日志 | ★ 沿用既有纪律：**不进日志、不进录制 manifest**。要有一条测试或 `grep` 证据 |
| 默认 | 合成角色是默认路径；照片是家长主动开的第二条路 |

**★ 两个 bug 是"在浏览器里点了一遍"才发现的，静态读代码都看不出来。**
共同点是：**在某个动作出现之前，错的那一版与对的那一版永远一致**。

1. `summaries()` 拿"扫目录取 revision 最大"当"当前版"。切回第 1 版之后，`latest`
   文件里明明写着 `1`，列表页还说第 2 版是当前。现在必须走 `load()`（它读那个指针），
   指针指不到东西时才退回最大 revision。用例写在 `store.test.ts` 的 `summaries` 那一组，
   组名的注释里写着它是怎么被发现的。
2. 形象页"从现在起用这一版"那颗按钮的条件是 `shown.revision > 1`，于是
   **切回第 1 版**——最常发生的那一次——根本没有按钮。判据只有一条：
   看的那一版**不是**现在在用的那一版。（同样由点击发现，注释留在 `ChildDetail.tsx`）

**这一刀刻意没做的判断**（每条都有具体理由，不是偷懒）：

- **不自动判"这条建议被采纳了吗"**。现有比对器问的是"图上有没有这几条锚点"，
  而这次动的正是锚点管的那些部位——"眼睛再大一点"会让"深棕色圆眼"判**不**像，
  于是**成功会被判成失败**。要自动判得先有"两张图 + 一句判据"这个新的比对形态。
  在那之前，**新旧两版并排给家长看**就是判据，而且它不需要免责话。
- **切回旧版不叫"撤销"、不二次确认**：它只动那个一字节的指针，不删任何一版。
- **`validateCard` 有和 `validateProfile` 一样的隐患**（对形状不对的输入不总收）。
  没顺手改：它属于建卡那条路，改了要连带动 02 的验收。

**★ 这一刀真正的收获是两个 bug，两个都是在"真跑 + 核查磁盘"里露出来的：**

1. **缩略图与卡片平级，删卡不删图。** `thumbs/<档>/cards/<cardId>/…` 在 `cards/` 之外，

   这不是推理出来的：开工前资产根里躺着 **9 个这样的残留**，全是我自己在前面几刀里

2. **`deletePrefix` 的两个实现对"前缀落在一个文件上"回不一样的数**：内存版按键前缀

### 四、★ 验证时发现并修掉的一个真缺陷（不是这次新写的，是两处改动撞出来的）

闭环探针（见下）跑出来的第一版结果里有这么一行：`mark:（没读到）`。
链起来看是这样：

1. 读照片这条路会**刻意清空**模型看不见的槽位（上面那条理由）；
2. 而本刀同一天给 `checkAnchors` 加了一条「空值也算问题」（补的是另一个会花钱的漏洞）；
3. `特征记号` 与 `常服` 是**软锚点**——`REQUIRED_SLOTS` 里没有它们，
   `normalizeAnchors` 丢掉它们之后卡照样合法。

三件事各自都对，合起来是：**家长读完一张照片，看到「记号是空的」，按钮点不动，
而那张卡本来完全合法**。而"照片里看不见记号/常服"是这条路上的常事
（这次实测的输入图就看不见）。

修法是**把"空值算错"限定在硬锚点**——判据一句话概括是
「**空值只在'缺了它会出不了图'的槽位上算错**」，因为上面那段"界面比服务端松"的
推理在软锚点上不花任何钱。改动在 `checkAnchors`（`card.ts`），配两条用例：
软锚点空着**不算**问题、硬锚点空着**仍然**算问题（不许把花钱那道缝一起放开）。

★ 值得记的是**它是怎么被发现的**：不是读代码读出来的，是**看探针的输出**
（那一行"没读到"）想起来"那界面会报什么"。所以探针要把**原始产物**打出来，
只打一个"通过/不通过"会漏掉这一类。

### 三、★ 我上一版那条断点是错的（这一刀实测抓出来的）

上一刀我写的两列断点是 `@media (min-width: 1100px)`，推导是按

错的后果不是"不够漂亮"，是**每一格都放不下值**：

| 视口 | 右栏实测 | 两列每格 | 七条示例值                   |
| ---- | -------- | -------- | ---------------------------- |
| 1100 | **349**  | **163**  | 溢出 24–98px，**七条全被切** |
| 1440 | 665      | 321      | 一条都不切                   |

判据本来就是"这一栏有多宽"，所以改成让它**量自己那一栏**：
`.nc__anchors { container-type: inline-size }` + `@container (min-width: 500px)`。

**阈值 500 的来路**（复现：`.out/probe-nc-width.mjs` 打印每格的 `scrollWidth − clientWidth`）：
最长的**非**常服示例值是「黑发偏软，左侧总有一撮翘起来」210px，加输入框左右内边距 24
→ 每格 ≥234；两列再加 24 的栏间距 → 容器 ≥492，取 500。低于它宁可长、不可挤
（与 `.cf__pair` 窄屏落回一列是同一条判断）。
★ 常服在 245px 的格子里仍差 16px（它的值是"一整套衣服"，235px），所以让它独占一行——
按位置选它是因为 `ANCHOR_SLOTS` 声明序里它就是最后一条；往槽位里加东西时先回来看一眼。

★ 值得记的是**两条错误都是"我以为的数"**：一条是算漏了侧栏，一条是探针第一个数块
标签写着 1440、量的其实是启动时那个 1280（已修）。两个都不会报错，只会让结论偏。

### 一、第八格为什么是「软」锚点、为什么排在**最后**（两个决定都是为了不弄坏磁盘上已有的东西）

1. **软，不是硬。** `checkAnchors` 只对**硬**槽位报空错（`REQUIRED_SLOTS` = hard only）。
   如果把补充做成硬锚点，**磁盘上每一张已有的卡**（七格，没有 `extra`）在 `validateCard`
   那一刻全部变成不合法——家长打开旧角色卡就得到一句"锚点不完整"，而卡上一个字都没改过。
   软锚点空着本来就合法，旧卡原样通过。语义上也对：补充是"还可以再说一句"，不是"必须说一句"。
2. **追加在末尾，不插在中间。** `ANCHOR_SLOTS` 的顺序不是排版顺序，是**提示词顺序与指纹顺序**：
   `normalizeAnchors` 按声明序排（`card.ts:145` 那句"排序是指纹稳定的前提"）、
   `promptFragmentOf` 按声明序拼、`cardDigest` 吃的就是排好的锚点数组（`card.ts:254`）。
   插在中间会让**每一张已有卡的指纹变**——内容没变、指纹变了，于是文件名里那个
   `ref.<指纹>.webp` 全部对不上，参考图一夜之间"丢了"。追加在末尾，旧指纹一个字节不变。

### 一、先回答"为什么"：**和照片清不清楚无关**

用户那句「照片信息已经很清晰了」是合理推断，但它指错了地方——这句报错发生在**模型读完
之后**，而排障原文那个括号里是**空的**。空括号说明 `content` 是空串：模型这一趟**什么都没写**。
照片清晰度决定的是"读到的东西准不准"，而这一次是"它根本没交卷"。

★ 我**没能复现**（这一点必须先说清）：真打 `kimi-k2.6` 五次（`.out/vision-raw-2.log` …
`-5.log`）五次都成功。所以下面这些不是"猜的原因"，是**从回包里读出来的机制**：

```
顶层键：id, created, model, object, choices, usage, cost_cny, billing_pending, trace_id
message 的键：content, role, reasoning_content, provider_specific_fields
finish_reason：stop
usage：completion_tokens 2526 · prompt_tokens 3094 · reasoning_tokens 2395
```

它是**推理模型**：一次读照片要产 2400+ token 的思考链，而正文只有 250 字上下。
"想完了没写"、"正文被上游截掉"都是这种模型**偶发**的坏法，而它偶发到什么程度——
五次里一次都没轮到（用户那次轮到了）。

### 二、真正确定的是**我们这一侧的两个缺陷**（都不依赖复现）

| #   | 缺陷                                  | 症状                                                                                                        | 改法                                                                                                                         |
| --- | ------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 1   | 读回包只认 `message.content` 一个字段 | 正文空时排障原文**是空的**，界面上那句"（原文前 120 字：）"没有下文；思考链明明有 4000 字，我们一个字都不看 | `readReply()` 一起捞 `content` / `reasoning_content` / `finish_reason` / `refusal`，失败时带上**思考链的末尾**               |
| 2   | 重试推给家长                          | 界面上写着"再点一次通常就好了"——等于让用户手动重试                                                          | 引擎自己试第二次（**只针对"拿到回包但内容不能用"**；`requestJson` 那条"4xx 不重试"不越过），界面改成如实说"已经替你试过两次" |

★ 第 1 条还顺手补了一个**静默**的洞：`content` 除了字符串还有**分片数组**形状

### 三、真正"每次都复现"的那一个：模型的表叫 `anchor`，我们只读 `anchors`

探针 `--dump=1` 打出来的真回包（就是用户那张半身照）：

```json
{
  "anchor": {
    "骨相": "圆脸、短下巴、脸颊鼓",
    "眼睛": "圆眼、黑瞳、双眼皮",
    "头发": "短发、齐刘海、别鸭夹",
    "头身比": "看不清",
    "肤色": "白皙、双颊泛红、肤色匀",
    "特征记号": "面部、耳侧黄鸭夹、腮红印",
    "常服": "无袖上衣、淡紫色、圆领"
  },
  "lookTags": [],
  "note": "照片仅显示头部及肩部，身体部分被截断。"
}
```

同一时刻生产那条路报的是「**✓ 读到了 0 条**」——`anchorsFromAnalysis(parsed['anchors'])`
收到 `undefined`，回空表，界面写「读到了 0 条」。**模型答对了，是我们没去取。**

★ 形状是模型**每次自己挑**的：同一张照片、同一份提示词，一次回 `anchors` + 中文槽位名，
下一次回 `anchor` + 英文槽位键。这不是提示词钉得死的东西，所以：

- **认表放宽**：`anchorsObjectOf` 先试约定名（`anchors` / `anchor`），再扫顶层"谁像表就是谁"，
  最后把整份 JSON 当平铺表；
- **认槽位不放松**：候选表要交给 `anchorsFromAnalysis`，里面**认得出至少一个真槽位**才算数——
  于是 `{score, missed, reason}`（比对那条路的回包）不会被误认成锚点表；
- `lookTags` / `note` 同理（`fieldOf`：顶层没有就往被挑中的那张表里再看一眼）。
  两个字段各有自己的判据（标签只留 `LOOK_TAGS` 里有的、note 只认非空字符串），多看一层不会放进脏数据。

提示词里也加了一句「锚点表固定放在顶层 `anchors`」，但**读回来那一侧不靠它成立**——
它只是把彩票的概率压低，不是判据。

### 一、那两句话

| 做的                                           | 在哪儿                                                                   |
| ---------------------------------------------- | ------------------------------------------------------------------------ |

### 二、出图那三步：它对应**两次真的请求**

```
● 档案存好了
◐ 正在画他的第一张形象 · 已等 12 秒
○ 画好了给你看
```

- `POST /api/children`（存档案）→ `POST /api/cards`（或 `/cards/photo`）→ 换成结果那一屏。
  哪一步是"现在"由 `stage`（`profile` / `image`，两个值）说了算——
  第一个请求通常一百毫秒就回来，但它是**真的**一步（它失败的话这一屏就停在它上面）。
- 秒数只在真正出图那一步数（`useElapsedSeconds(busy && stage === 'image')`）：
  存档案那一下不该算进"画了多久"。
- 仍然**没有百分比**：出图那条请求也是一次性回包，中间读不到进度。
- 位置在`右上角`——那颗按钮的老家，判据与错误本来就住那儿。
  ★ 那里继承的是 `text-align: right`（`.nc__head-act`），所以 `.nc__steps` 显式
  按回左边：一行一个圆点，几行的圆点要排在同一条竖线上；
  `align-items` 也从 `center` 改成 `baseline`（右上角那一档窄，长句折行时
  `center` 会把圆点压到两行中间，看起来像它标的是第二行）。

实测（`preview_eval` 取 DOM 与计算值，两次请求都 stub 住）：

### 一、秒数 → 轮播的四句话（两处）

| 位置   | 播什么                                                                                    |
| ------ | ----------------------------------------------------------------------------------------- |
| 读照片 | 正在加急处理中 → 正在一格一格地看这张照片 → 正在把看到的东西记下来 → 快好了，再等一小会儿 |
| 出图   | 正在加急处理中 → 正在铺底色 → 正在一点点上色 → 快好了，再等一小会儿                       |

- ★ 这一段值得写清楚：**换掉的是一条真读数**。秒数说的是事实（确实等了这么久），
  而「正在加急处理中」是一句**语气**。所以这几句立了一条纪律，写在 TSX 注释里：

- 秒数那一格原来的 `aria-hidden` 保留：`role="status"` 会在开始时念一次三步，

## 2026-10-16 · 第 27 刀：**点了「删掉他」不弹窗** —— 那一下根本没落在这颗按钮上

用户报障（截图是卡片墙，圈住卡片右下角的「删掉他」）："点击删除没有出现弹窗啊，你好好检查一下"。

**用户是对的，我前面三轮的"验过"是假读数。**

### 一、症状与成因

那一下点下去落到的是**整卡覆盖层** `A.cw__open`（"点哪儿都进详情页"那一层），不是按钮——
所以既没有弹窗，也不是"什么都没发生"，而是**跳去了详情页**（而那一屏现在没有删除入口，
于是看起来就像"删除坏了"）。

成因是一层**看不见的笼子**：

```
.cw__show          ← 悬停时 transform: translateY(-6px)
  .cw__fold
    .cw__reveal    ← z-index: 2（为了压在 .cw__open 的 1 之上）
      .cw__reveal-actions
        button.cw__del
```

`transform` 会造出一个**层叠上下文**，于是整棵子树的 `z-index` 被关在里面：
`.cw__reveal` 的 2 只在 `.cw__show` 内部有效，而 `.cw__show` 这个笼子整体
在 `.cw__open`（正 z-index）**之下**。`character-wall.css` 里那条注释
（"第五轮那两颗搬进了 `.cw__reveal`，而那一层自己就是 z-index: 2…所以逐颗再抬一次已经没必要了"）
**是错的**——它漏算了中间夹着的 `.cw__show` 在悬停时变成层叠上下文这件事。
★ 这颗按钮从第五轮起就点不动（`查看详情` 那颗也一样，只是它本来就去同一个地方，
所以五轮没人发现），**这一刀没有引入它，是把它暴露了**。

### 二、修法：把"抬 6px"从 `transform` 换成 `top`

```css
.cw__show {
  position: relative;
  transition: top …;
} /* 新 */
.cw__card:hover .cw__show {
  top: -6px;
} /* 原来是 transform: translateY(-6px) */
```

位移一样是 6px，但 `position: relative`（`z-index: auto`）**不造层叠上下文**，
于是 `.cw__reveal` 的 `z-index: 2` 真的能和 `.cw__open` 的 1 比大小了。
代价是这一下走**布局**而不是合成层——一张卡悬停时挪 6px，可以接受；
另一条路的代价是"点了删除却跳页"。

★ 顺带修好的一处**自己刚踩的坑**：改机制时我把静止档（`prefers-reduced-motion` 与 `hover: none`）
那一段的选择器表剖开，剖错了位置，**把 `.cw__mat` 的 `transform: none` 吃掉了**——
那会让触屏上缩到 0.9 的那张画再也回不来。复查时抓回来的，三段现在各自复位各自的属性。

### 三、判据（`elementsFromPoint`，A/B 同一次会话里）

| 量法                                 | 栈顶（按钮中心的命中顺序）                                                  | 结论     |
| ------------------------------------ | --------------------------------------------------------------------------- | -------- |
| 老机制 `transform: translateY(-6px)` | `A.cw__open` → `BUTTON.cw__del`                                             | ✗ 点不到 |
| 新机制 `top: -6px`                   | **`BUTTON.cw__del`** → `.cw__reveal-actions` → `.cw__reveal` → `A.cw__open` | ✓ 点得到 |

真点一次（点的是 `elementFromPoint` 给出的**那个元素**，也就是真鼠标会落在的东西）：
`hydrated=true` · 落点 `BUTTON.cw__del` · 路径仍停在 `/character` ·
弹窗出现「删掉 小乐？」+ 那句警告 + `确认删除 / 算了`。

### 四、★★ 为什么前三轮没验出来（这条比 bug 本身值钱）

我三次用的都是 `element.click()`——**程序化点击绕过命中测试**：
它不看 z-index、不看遮挡、不看你有没有真的悬停在那儿。
于是"按钮能点"这个结论在一个按钮被整层盖住的页面上**照样成立**。

1. **量遮挡要用 `document.elementsFromPoint(x, y)`**（复数），它给的是完整命中栈，

   那时栈顶必然是 `.cw__open`（这一口差点让我把"没坏的东西"改一遍：第一次量到

### 一、为什么是弹窗：那列小字真正的毛病是**位置**，不是字号

改动之前，这一屏的判据与错误住在**标题行右上角**（`/character/new` 第七刀把按钮挪那儿时
一起搬过去的），等待的三步也住在那里。而用户填完名字 / 照片 / 八条锚点之后，
**视口多半停在左下**——他按完按钮，视线根本不在那一角。
判据看不见就等于没有；"正在画"看不见就等于卡住了。截图里那两个红圈是同一个病。

所以这一刀不是"把字放大"，是**把这件事搬到屏幕正中**：那几十秒里，
这一屏此刻唯一在发生的事就是它，它不该躲在角上。

### 二、四件活各说什么（★ 而**为什么有的活没有三步**）

`components/studio/wait-copy.ts`（纯函数）是**唯一**一处写这些话的地方：

| 活                      | 请求                      | 几步     | 时长           |
| ----------------------- | ------------------------- | -------- | -------------- |
| `analyze` 读照片        | 1 次                      | 三步     | 实测约 45 s    |
| `draw` 出他的第一张形象 | **2 次**（存档案 → 出图） | 三步     | 一瞬 + 约 24 s |
| `revise` 重画一版       | 1 次                      | **没有** | 十几秒         |
| `first` 给出第一张      | 1 次                      | **没有** | 十几秒         |

★ 三步不是凑的：每一步都对应一个真事件（`draw` 是两次真请求 + 一次落地，
由 `stage` 说现在在哪一段）；`analyze` 的第一步是"照片选好了"（事实）、
第三步是"接下来会发生的事"（写出来是因为用户此刻最想知道"等这么久等的是什么"）。
★ 反过来，**只有一次请求的活就不编三步**——给 `revise` 编一条"正在理解你的建议"
就是编进度。这条有**机器版**：`wait-copy.test.ts` 断言 `revise` / `first` 的 `steps` 为空，
并且那几句轮播的话里**不出现数字与百分号**（"只说还在办，不说办到哪儿了"）。

★ 一处**刻意保留的不同**：`draw` 在"正在存他的档案"那一段**不播**那句话
（`lines: image ? DRAW_LINES : []`）。存档案是一百毫秒级的本地写，不是"在等模型"——
冲它说「正在加急处理中」是把一件不慢的事说成慢的（第 21 刀定过这条，这一刀照旧）。

### 三、顺手关掉的一个洞：两件"要等"的活**原来能同时在飞**

### 一、第 2 句的真因：不是"没刷新"，是**刷新要几秒**，而屏幕在那几秒里说假话

先排除掉的两条：

- **不是服务端没写进去**：磁盘上 `latest` 与 `rN.*.json` 都是对的，手动刷一下就有。
- **不是客户端路由缓存**（`next.config.ts` 的 `experimental.staleTimes.dynamic = 30`）：
  把它临时改成 **0**、重启、再测，**照样**——所以那个数改回去了（它是一个量过的取舍，
  这一刀没有理由动它）。

真正量到的是这个（本机 3324，点「从现在起用这一版」那一下，每 0.5 秒读一次 DOM）：

| 时刻          | 屏幕上                                                               | 磁盘   |
| ------------- | -------------------------------------------------------------------- | ------ |
| +0.5 … +2.0 s | （请求还在飞，还没有任何字）                                         | 旧     |
| **+2.5 s**    | notice 已经是「现在用的是第 2 版」，而历史里**还是**「第 1 版 用它」 | **新** |
| +2.5 … +6.3 s | 一直停在这个自相矛盾的样子                                           | 新     |
| **+6.8 s**    | 历史终于变成「第 2 版 用它」                                         | 新     |

也就是说：`router.refresh()` **会**把新数据送进来，但这一次要**约 4.3 秒**
（要重跑一遍服务端组件：读盘 + 问后端鉴权 + 渲染；dev 下还要现场编译）。
用户就是在这几秒里看图的——他看到的是"第二版没出现"，于是手动刷新一次
（那一刻恰好已经换好了）。同一条 RSC 读（手写 `?_rsc=` 请求）拿到的是**新的**
（`"digest":"e933fda59817","isCurrent":true`），所以也不是"读回来的是旧的"。

### 二、修法：**把那几秒说出来**，外加一条兜底

新加一个中间态 `Arriving`（`ChildDetail.tsx`）：写成功之后**不立刻宣布"已经好了"**，
而是问服务端那份数据"换上来没有"（`arrived()`：这一版在不在清单里 / 指针挪没挪过去 /
档案名字对不对），在它到达之前那行字是「正在把它换上来…」：

| 件数             | 写完之后先说                   | 换上来之后说                            |
| ---------------- | ------------------------------ | --------------------------------------- |
| 重画一版         | 第 N 版画好了——正在把它换上来… | 第 N 版画好了。往下看历史，上一版还在。 |
| 出第一张         | 第 N 版画好了——正在把它换上来… | 第一张形象画好了。以后做书都用它…       |
| 从现在起用这一版 | 指针动了——正在把这一版换上来…  | 现在用的是第 N 版。以后做书都用它…      |
| 改基础信息       | 档案改好了——正在换上来…        | 档案改好了。以后做的书按新的来…         |

★ **判据是"等那件事出现在 props 里"，不是"等固定几秒"**——服务端回得快就一闪而过。
★ 兜底：**8 秒**还没换上来就 `window.location.reload()`（用户手动做的就是这件事）。
8 是这一段里唯一可以商量的数：实测那次是 4.3 秒，8 是它的近两倍

又短到"用户还没开始怀疑页面坏了"。

## 第 30 刀：删掉提示句里那对括号（2026-10-22）

★ 第七节那条「换行会折成半角空格」的坑**仍然有效**，只是这次它落在 `；` 后面：
`</strong>` 与那个字符串仍是两个兄弟节点，中间那个只含换行的空白文本节点会被 JSX
剔掉。核法不是读源码，是把这一段 JSX 交给 `tsc --jsx react-jsx` 编译一遍看生成的
children —— 出来是 `["…读的，", <strong/>, "；", "照片里没有的我留空了——…"]`，
没有空白字符串，`renderToStaticMarkup` 出来的也正是上面那一句，`；` 和「照片」之间
没有缝。
