# 02 · 参考图通路：引擎加一条 `edits`，上传图做归一

Status: open
依赖：[01](01-model-selection.md)（结论已有）；被 [03](03-character-profile.md) 依赖
硬约束：这条通路的实现**必须留在 `src/lib/engine/providers/`**，组件里一行 fetch 都不许有
（`lib/engine/` 不得 import React，且"一个 node 脚本能跑完整本生成"是 #11 的证据本身）

## 二、要做的事

### 2.1 归一化必须在**服务端**做，且是一条可测的纯函数

上传的是用户手机里的照片：HEIC/JPEG/PNG、带旋转 EXIF、可能 4000×3000、可能带 alpha、
可能 80 KB 也可能 12 MB。这些都得在**送进 provider 之前**变成一个已知形状。

- 落点：`src/lib/engine/image/normalize.ts`（新目录，纯函数 + `sharp`）
- 签名形状：`normalizeReference(bytes, {maxSide}) → {bytes, mime, width, height, flattened}`
- **必须报回**它做了什么（压平了 alpha？缩到了多少？），因为用户要能在界面上看到
  "我们处理了你的照片"而不是猜
- 边界：小于 240 的正方形要**放大**还是**拒绝**？→ 拒绝并给出人话文案
  （"这张照片太小了，至少要 240×240"）——静默放大会给出一张糊的插画，比报错更糟

**测试**：`normalize.ts` 是确定性逻辑，走既有 tdd 路线（[w2 工单 09]）。
输入 fixture 至少覆盖：1×1、240×240 边界、8000×8000 边界、带 alpha PNG、
带 EXIF 旋转的 JPEG、12 MB 大图。`sharp` 在 node 环境里可用（W1 已见过它解析 `.pnpm` 绝对路径）。

### 2.2 引擎的 provider 侧：`ImageProvider` 加一个能力位

现有适配器 `tokenrhythm-image.ts` 只走 generations。要加的是**同一家、第二条路由**，
所以不新建 adapter，加一个方法：

```ts
// providers/types.ts 的形状（示意，按实际类型走）
interface ImageProvider {
  generate(req: ImageRequest): Promise<ImageResult>
  // 可选：支持参考图的 provider 才实现。不支持时由调用方给出人话错误
  edit?(req: ImageRequest & { reference: ImageReference }): Promise<ImageResult>
}
```

`IMAGE_SUPPORTS_REFERENCE=0` 这个环境变量**要翻成 1，或者干脆删掉**——它是 W1 那条
错误结论的化石。倾向**删掉**：能力由"provider 有没有 `edit`"表达，比一个可能忘记同步的
字符串开关更难骗。（若保留，理由是"同一家也可能只有部分模型支持"，那就在
[01](01-model-selection.md) 的探测脚本里量出这个开关该取什么值，而不是手填。）

### 2.3 失败要分得开

三条服务端错误码各自对应一句不同的用户话，**不许合并成"生成失败"**：

| 服务端                           | 界面                                                                     |
| -------------------------------- | ------------------------------------------------------------------------ |
| `IMAGE_INPUT_DIMENSIONS_INVALID` | 照片太小/太大，并说明是**参考图**的问题不是在生成的问题                  |
| `IMAGE_INPUT_ALPHA_UNSUPPORTED`  | 这条在我们归一化之后**不该出现**——出现了就是 bug，报"内部错误"并附 trace |
| 超时                             | 15s 是实测的常态，超时阈值要明显高于它                                   |

★ 最后一条是这一单最容易糊弄的地方：**"我们归一化过了"这句话要能被证明**。
做法是归一化后把尺寸/通道数记进 `events.jsonl` 的一条 `debug` 事件里，
于是下次真出现 alpha 错误时，事件流里躺着那张图的形状。

## 四、实测结果（2026-10-15，可复现）

跑法：`node scripts/e2e-image-reference.mts`（`--dry=1` 可以只跑不发请求的两节）。
产物在 `.out/e2e-image-reference/`，`report.md` 可直接贴。

### 4.1 归一化（把角色卡那张插画**原样**喂进去，不让它绕过这一层）

|       |                                                     |
| ----- | --------------------------------------------------- |
| 进去  | 1440×1440 · png · **4 通道 · alpha=true** · 2.69 MB |
| 出来  | 1440×1440 · png · 3 通道 · alpha=false · 2.21 MB    |
| notes | 透明通道压平到白底（接口明说不支持带 alpha 的 PNG） |

★ 这条改写了一个隐含假设：**"归一化是给手机照片准备的"**。实测下来我们**自己的**
产物（角色卡那张 PNG）就是 4 通道带 alpha 的，不归一化根本送不出去。
所以这一层不是"用户输入的卫生处理"，是**每次调用都在路径上的一环**。

### 4.2 失败路径（每次跑都走一遍，不是一次性结论）

|                              |                                       |
| ---------------------------- | ------------------------------------- |
| 送的什么                     | 200×200 PNG（短边低于服务端下限 240） |
| 引擎抛的码                   | `reference-invalid`                   |
| 界面回的状态码               | 400                                   |
| 能不能重试                   | 不能                                  |
| 界面上第一句                 | 这张照片不能用作参考图                |
| 对照 `card-invalid` 的第一句 | 角色卡不合格，引擎拒绝开跑            |
| 两句是否不同                 | **不同**（两句一样脚本会自己抛错）    |

### 4.3 端到端（`edit`，经引擎自己的适配器）

|                  |                                                                          |
| ---------------- | ------------------------------------------------------------------------ |
| 路由             | `POST /images/edits`，走 `createTokenrhythmImage().edit`，不是手搓 fetch |
| 提示词           | 生产那一条（`prompts/image.ts` 的 `pagePrompt` + demo-plan 第 1 页）     |
| 参考图是否进请求 | 是（`referenceApplied === true`，否就抛错）                              |
| 耗时             | 9.4s / 9.8s / 9.9s（三次）                                               |
| 产物             | **1024×1024** · png · 4 通道 · alpha=true · 1.75–1.85 MB                 |
| traceId          | `trace_225829d2…`、`trace_0a23cf94…`、`trace_a0490fc6…`                  |

★ **产物是 1024²，不是请求里写的 1440²**——`edits` 那条路没有 `size` 字段，
尺寸由模型定。页图的构图约束是按 1440² 写的，所以这个数直接写进了
`illustrate.ts` 的 `referenceForPages` 注释里（开了它，页图尺寸会变）。
**"变小了 30% 对书里那一页够不够"仍然没看**，所以那个开关仍然默认关。

### 4.4 看图核对（验收原文："与 §一 那次一致"）

人看，逐条对 `checklistOf(card)` 那五条（**与比对器用的是同一个函数**）：

| 锚点                               | 结论             |
| ---------------------------------- | ---------------- |
| 骨相：圆脸、颊部饱满、下颌线软     | 一致             |
| 眼睛：深棕色圆眼、眼距略宽、睫毛短 | 一致             |
| 头发：黑发偏软，左上方永远翘着一撮 | 一致             |
| 头身比：约 1:4，四肢圆润           | 一致             |
| 肤色：暖黄偏深                     | 一致             |
| 常服：芥黄短袖 + 深蓝短裤 + 红雨鞋 | **一致**（见下） |

★ §一 那张表最后一行写的是"**衣服配色有偏差**"。这次**没有偏差**，原因查出来了：
§一 那次送出去的提示词是手写的，里面有"**暖色调**"三个字，而锚点写的是"芥黄短袖"——
**红是提示词自己推出来的**，不是通路的问题。换成生产的 `pagePrompt`（它只拼锚点，
不加风格形容词）之后，上衣就是芥黄。
那次观测因此**作废**：不能拿它当"通路保真度"的证据。这也是脚本默认走生产提示词的
理由——**提示词是变量，量"通路"的时候必须把它摁住**。

★ 另一条非文本证据：衣服胸口那道**白色波浪纹样**在产物里也出现了，
而**七条锚点里没有它、生产提示词里也没有它**——它只可能来自参考图。
"参考图真的进了请求"因此有了一个不依赖 `referenceApplied` 这个布尔值的旁证。

### 4.5 12 MB 大图（§2.1 六类里唯一需要造的那一类）

实测 **12.58 MB → 5.94 MB（0.47×）**，1440×1440。

★ 这条纠正了我自己的一个错误期待：我第一版把断言写成"缩到 3 MB 以内"，跑出来红了。
不是代码错——**PNG 是无损的**，高熵图（真照片就是高熵）缩到 1440² 之后仍然很大。
于是那条断言改成了"确实变小了"，绝对量级写进注释当事实、不当闸门。
**一个测出来的数拿来当阈值，下次换个 fixture 就红，那是占卜不是测试。**

## 五、还欠着的（不许用上面任何一行顶替）

1. **`pnpm build` 红**，且**不是这一单弄红的**。症状、定位与复现步骤在
   [11-client-manifest-build.md](11-client-manifest-build.md)——它红在首页的
   `StorybookFlip.tsx` 上，而 02 一个首页文件都没碰过。
2. `edits` 的**计费**：没量到。适配器的 0.20 元/张是从 generations 挪过来的兜底值。
3. **照片**当参考图画出来的像不像：没量到（要用户提供照片；而且比对器那一环——拿照片比插画——同样没量）。
4. `edits` 能不能指定尺寸：没试过（只送过 model / image / prompt 三个字段）。
5. **上传通路上没有 body 体积上限**：归一化能吃掉 12 MB，但"我们这边收多大的图"没量过，
   因为上传路由还没做（3.2 的结论就是不做）。
6. `card-invalid` 回的是 **502**，而 `reference-invalid` 是 400。两个都是"输入不合格"，
   状态码却不一致——本单**故意没动它**（改它是另一条码的事，顺手改会把两件事混在一次提交里）。

### 2026-10-15 · 主体完成

交付物：`src/lib/engine/image/`（`normalize.ts` + 14 条测试）、
`tokenrhythm-image.ts` 的 `edit()` 与 `supportsReferenceOf`、

`scripts/e2e-image-reference.mts`。

三件本来会变成谎话、这次被摁住的事，各记一条：

1. **`supportsReference: true` 是手填的**，而 `types.ts` 和测试都说它是推导出来的。
   手填的那个值在被漏改的那天不会响。改成导出 `supportsReferenceOf(impl)`，
   并加了一条测试：喂一个**没有 `edit` 的实现**进去必须得 `false`——
   否则把推导换回字面量 `true` 不会红任何东西。
   ★ 顺带修正了 W1 的结论**范围**：7 个候选字段名在 **`/images/generations`** 上确实全被
   400 挡回，这件事仍然成立；被推翻的只是"所以这家做不了图生图"。两条结论各管各的路由，
   合并成一句就是把**路由级事实**讲成了**模型级事实**。
2. **`card-invalid` 曾给照片问题配了锚点的指引**。这是真的界面缺陷（验收第 6 条要的
   正是这个）：家长拿"回第 3 步改锚点"不知道该动哪里。拆出 `reference-invalid`，
   走 `byCode` + `httpStatus` 分流，测试钉住两条码**必须不同**。
3. **界面上那句假话**：第 1 步写着"图像接口不支持参考图"。事实是支持，缺的是**消费方**
   （卡上的参考图既要逐页画、又要用来比对，拿照片当参考图意味着"拿照片比插画"，
   没量过）。所以**框继续不做**，但文案改成说真话。

`scripts/probe-image-reference.mts` 的文件头也补了一段：它探的是 `/images/generations`
的请求体，那 7 个候选名在**那条路由上**至今不存在——**本文件一行都没被推翻**。
