# 05 · 生成编排：表单 → `BookRequest` → `runBook` → 阅读器

Status: open
依赖：[02](02-event-stream-transport.md)、[03](03-model-and-key.md)、[04](04-creation-flow.md)

## 一、做什么

把已填的五步拼成引擎的入参，调 `/api/books`，把事件流喂给过程面板，
完成后进阅读器。**这一单是"独读版全链路"真正闭合的地方**。

```
表单状态 ──toBookRequest──▶ BookRequest ─┐
表单状态 ──toEnv──────────▶ Env ─────────┴─▶ POST /api/books ──▶ createProviders({env, mode:'live', store})
                                                                        │
                                                  runBook(request, {providers, onEvent}) ──▶ SSE ──▶ 过程面板
                                                                        │
                                                              完成 → /reader/<bookId>
```

两条都是**纯函数**（`toEnv` 在 [03](03-model-and-key.md)，`toBookRequest` 在这里），
一起进工单 [09](09-validation-tdd.md) 的 tdd 范围。

### 存储根

`ASSET_ROOT`（缺省 `.out/web`，已在 `.gitignore` 里）。用 `createFsStore(root)` +
`createCardStore(store)`。理由：W1 的 `.out/` 已经证明这条路径能跑，
而"生成产物是运行期数据，不是资产"这条判断在 `.gitignore` 的注释里已经写过一次。

### 页数

默认 20（产品定义的独读版）；表单上可改（演示用 5–8），
因为它本来就是入参不是常量（`BookRequest.pages` 的注释写着这句话）。
**界面要把"20 页大概要多久"如实说出来**，不要让家长点完才发现要等十分钟。

## 二、过程面板：只用 durable 事件，文案不许抄第二份

| 用什么             | 从哪来                 |
| ------------------ | ---------------------- |
| 这一条该不该占一行 | `isDisplayable(event)` |
| 这一行写什么人话   | `describeEvent(event)` |
| 阶段名（"正在画"） | `STAGE_LABELS[stage]`  |

★ `events.ts` 的文件头写着"一句话人话放在引擎侧而不是 UI 侧：MCP 返回与日志也要同一句话，
不能各翻一遍"。**界面里不许再写一份文案表**——写第二份的那天起，
MCP 返回与屏幕上就会出现两句不一样的话，而没人会发现。

客户端只 `import` `@/lib/engine/events.ts` 的那三个导出，**不 import `engine/index.ts`**
（index 会把 registry 与 stores 一起拖进客户端 bundle 图；现在没炸只是因为拼写运气好，
不该靠运气）。

### 面板要显示什么（判据：家长看了会改变对进度的理解）

- 规划：`stage` 起止 + `plan-ready`（标题、页数、几个选择点）
- 逐页：`illustration`（第 N 页画好了）、`consistency` 只显示**非 pass**的
  （通过的 20 条会刷满屏，把真正的异常埋掉——`isDisplayable` 的注释已经写明这条判据）
- 重画：`retry`，带上原因（"第 9 页不太像，正在重画（第 2/3 次）：相似度 0.71 低于 0.75"）
- 失败：`error` 非致命 → "第 N 页退回了"，**不白屏、不终止整条流**
- 完成：`book-ready` → 出"进入阅读"

## 三、耗时与并发（★ 用实测决定，不用偏好决定）

逐页是串行的（`illustrateAll` 的注释里写着"并发是 W2 的优化"）。
一页 = 出图（实测十几秒）+ 视觉比对（两张 1440² 的图，几十秒）。**20 页串行是分钟级的两位数。**

规则写死在这里，免得临场改主意：

1. 先量**串行整本**的真实耗时（`pages=5` 与 `pages=20` 各一次，记进 Comments）
2. **只有当 `pages=20` 实测 > 8 分钟**时才做并发池，上限 3（防限流）
3. 做了并发以后，`seq` 仍是发射顺序（事件工厂保证），所以界面不需要按页号排序——
   但**过程面板要能同时显示多页在飞**，这一条要在实现时就摆好，别等并发上了再改渲染

★ 同时要把 `illustrate.ts` 那句注释改掉：写成"并发是 W3 的优化（10/13 从 W2 挪后）"。
**一句与计划不符的注释，就是下一个人读错代码的入口。**

## 四、失败与"这一页缺"

- 引擎已经把硬失败页记进 `Book.errors`，且 `illustrateAll` 保证"一页失败不等于一本书失败"
- 界面要**如实显示**：`stats.nodesGenerated < stats.nodesPlanned` 时是"20 页里做出来 18 页"，
  不是"完成！"
- 阅读器里缺图的页要有**语义诚实的兜底**（见 [06](06-reader-solo.md)），不许留裂图

### §三 的阈值：**由下界判定，成立**

§三 只要一个判断——"20 页 > 8 分钟"。串行流水线里每页**至少**要出一次图，
所以"一次出图尝试要多久"直接给出下界。这个数是量的，不是外推的：

```
命令一（落图时刻）：stat -c '%y %n' .out/web/books/xiaolu-r1-bf84901c4fcd/*
命令二（运行起点）：book.json 的 mtime − stats.elapsedMs = 19:04:56 − 2964.1s = 18:15:32
```

| 落图时刻         | 距上一次 | 这一段里发生了什么                       |
| ---------------- | -------- | ---------------------------------------- |
| p1-a1 18:16:42.9 | 70.2s    | 距本次运行起点（= p1 出图 + 比对）       |
| p2-a1 18:19:40.8 | 177.9s   | p2 第 1 版：出图 + 比对 + 判重画         |
| p2-a2 18:22:40.8 | 180.0s   | p2 第 2 版                               |
| p2-a3 18:26:00.5 | 199.6s   | p2 第 3 版（这一版过了，0.20 仍是 fail） |
| p3-a1 18:28:23.3 | 142.8s   | p3 第 1 版（出了图，之后中断开始）       |

```
运行起点 → p3-a1 落图 = 770.5s = 12 分 51 秒，含 5 次出图尝试
⇒ ≈154 s/次尝试（出图 + 比对 + 重画判定）
⇒ 20 页至少 20 次尝试 ⇒ ≥ 51.4 分钟
```

**51.4 分钟是由"每次 154s"推出的下界，> 8 分钟 ⇒ §三 的条件成立。**
它也和 §二 那条"2.5 分钟/页 → 约 50 分钟"吻合——但那条是**外推**，这一条是**从 mtime 量的**。

**决定（按 §三 的规则）：并发池该做，上限 3，且优先并发比对。**
判据是"下界已过线"，不是"我觉得它慢"。**落地是独立一单，本单不含。**

### ★ 更要紧的缺口：一次抖动吃掉了一整本

今天真正的教训不是"慢"，是**17 页在 36 分钟里全军覆没**——而它们只要等一会儿就能画出来。

- `requestJson`（`providers/http.ts`）**没有重试循环**。
- `shouldRetry` 定义了、写了注释、**没有任何调用点**
  （`grep -rn shouldRetry src scripts` 只命中它自己和 `w1-text-bakeoff.mts` 的一句引用）。
- 页级重试（`illustrateNode` 的 `maxAttempts`）只在**比对给了低分**时触发；
  出图**抛异常**时直接冒到 `illustrateAll` 的 catch，一页只走一次。
- 这条风险**早就写在纸上了**：`scripts/w1-text-bakeoff.mts:327` 的原话是
  "POST 按纪律不重试（见 http.ts:shouldRetry），**一次抖动就吃掉一整本**"。
  今天它从注释变成了实测。

★ 为什么不能简单地把 POST 也重试：**"出图超时不许重试"那条纪律针对的是"请求已经送到、
服务端可能已建单"**。而 `fetch failed`（DNS 失败 / 连不上 / 连接被拒）意味着请求
**根本没到服务端**，重试是安全的。麻烦在于这两者在 `fetch failed` 这**一个字符串**底下分不开，
因为报错把 `err.cause` 丢了：

```
实测原文：/images/generations 网络错误：TypeError: fetch failed
```

`ENOTFOUND` / `ECONNREFUSED` / `ETIMEDOUT` / `ECONNRESET` 四种处置完全不同，
而它们在这条消息里长得一模一样。**先修这条消息**（把 `err.cause?.code` 带上），
再决定重试策略——否则就是拿一个更弱的事实去回答一个更强的问题。

### 另外两笔账（要摆出来，不是顺手改掉）

1. **`imageCalls` 是下界，这一趟少算 1 次。**
   `index.ts:309` 的算法是 `Σ 已记录页的 attempt + errors.length`（注释写"失败的页也算，钱已经花了"）。
   而 `page-3-a1.png`（4,204,329 字节）**是画成了、落了盘、付过钱的**：
   p3 的 attempt 1 出了图、没过比对，attempt 2 才撞上中断超时。p3 没有 illustration 记录，
   于是只按 1 次计入。**实测真值 23，账上 22。** 要修就得把"失败页试了几次"也记下来。
2. **一轮重试失败，会把上一版已经付过钱的图从书里丢掉。**
   同一件事的另一面：p3 磁盘上有图、`book.json` 里没有，错误消息写的是
   `/images/generations 超时或中止`，而事实是"第 1 版出了图但没过比对，第 2 版没出成"。
   **比对调用失败那条路已经被刻意接住了**（`illustrate.ts` 里那段长注释就是为它写的）；
   **出图在重试轮里失败这条没有**。消息与事实不符，就是下一个人读错代码的入口。

### 这一格的结论

- ✅ §三 的 8 分钟阈值：**成立**（下界证据，不是外推）→ 并发池该做
- ❌ "串行整本耗时"：**没量成**，被 36 分钟中断污染。要这个干净的数得再跑一趟 20 页
  （约 40–50 分钟 + 一次出图开销），而它**不影响并发这个决定**
- ⛔ 重试：**缺口**，比并发更要紧；先修报错消息带上 `cause.code`

### 一、报错消息（`describeNetworkError`）

- `providers/http.ts` 新增 `describeNetworkError(err)`：顺着 `cause` 与 `AggregateError.errors`
  往下走（深度 3），把 `ENOTFOUND` / `ECONNREFUSED` / `ETIMEDOUT` / `UND_ERR_CONNECT_TIMEOUT` /
  `ECONNRESET` / `UND_ERR_SOCKET` 这些 code 带进消息，并各配一句**能定处置**的话。
  `requestJson` 与 `requestSse` 两处 catch 都换成了它。
- ★ 两句话是**分开写的**，因为它们的处置相反：`ENOTFOUND` 是"请求没到服务端"（重试安全），
  `ECONNRESET` 是"可能已经处理过了——**这一种重试不一定是安全的**"。
  把后者也说成前者，就是诱导出重复扣费的重试。
- 取不到 code 时**照实说取不到**（返回原来的 `TypeError: fetch failed`），不编一个。

### 二、连接级重试（用户批准的口径）

口径是用户 2026-10-15 拍的：**上限 1 次，只放行"确定没到服务端"的那几种**。
`isSafeToRetryNetwork(err)` 三条从保守那一侧取的纪律：

1. **判不出 code 就不重试**——拿不到判据时，"不重试"是唯一不花钱的那一边。
2. **混着出现就不重试**：`AggregateError` 里只要有一个 `ECONNRESET`，整次都不重。
   多地址并发连接时，"有一部分可能已经送到"就等于"可能已经建单"。
3. **超时/中止不走这条路**（调用点先挡掉 `AbortError`），"生成类超时不许重试"那条纪律一个字没松。

放行集合：`ENOTFOUND` / `EAI_AGAIN` / `ECONNREFUSED` / `ETIMEDOUT` / `UND_ERR_CONNECT_TIMEOUT`。
不放行：`ECONNRESET` / `UND_ERR_SOCKET`。

★ **它治的是抖动，治不了断网**——这句必须写清楚，否则下一个人会以为 10/15 那次事故被修好了：
退避只有 **1.2s**，而那次中断持续约 **36 分钟**，多等 1.2 秒救不回那 17 页。
要扛住那种量级，得做"整本跑完再回头补失败的页"，**那件事没做**，
它是独立一单，别拿这个重试当它的替代品。

## 六、出图 / 落盘失败时不许丢掉**已经画好的**图（2026-10-16 补）

§四 的口径是"一页失败不等于一本书失败"，这一节补的是它的**反面**：
一页**成功过**，也不该因为后面一次失败而变成"没做出来"。

### 症状（真跑出来的，不是推演）

整本 `xiaolu-r1-ee69012def18`（2026-10-16，20 页独读版）里第 6 页被记成"没做出来"：
`book.json` 的 `errors` 里有它、`illustrations` 里没有它，阅读器照实渲染兜底框。
**但磁盘上躺着一张完整可用的图**——`page-6-a1.png`，1536×1024、3.0 MB，
`/api/assets/...` 请求它照常 200。

事件流把经过写得很清楚：

```
[43] 第 6 页画好了               ← 第 1 次成功，图已落盘、已付费
[44] 第 6 页的小主角不太像        ← 比对没过
[45] 第 6 页不太像，正在重画（第 1 / 3 次）
[47] 第 6 页：下载媒体网络错误：TypeError: terminated · ECONNRESET
```

第 2 次尝试在**下图那一跳**撞上 `ECONNRESET`（`tokenrhythm-prod-backup-oss.oss-cn-beijing.aliyuncs.com`，
正是 `http.ts` 的重试白名单**刻意不放行**的那一类），异常冒到 `illustrateAll` 的 catch，
于是这一页**连同已经付过钱的那张 a1** 一起从书里消失。阅读器上那句"这一页没做出来"是**假话**。

### 根因：同一个文件里为比对那一跳修过，另外两跳没修

`illustrate.ts` 的重试循环里，只有 `opts.vision.compare` 包了 try/catch（180–189 行那段注释
记的就是"这一页连同已经画完、已经付过钱的图一起从书里消失…那是假的"）。
**真正画图与下图那两跳没有**——而它们才是每一页必然要走的。
这与降级 B 的既定语义也冲突：a1 只是没通过比对，本该以 `needsHumanReview: true` 进书。

### 修法

两条产出路径（① `image.generate` / `edit`，② `store.put`）各自包 try/catch，
统一走新的局部函数 `produceFailed(err, attempt)`，判据只有一条：
**手上有没有一张画完的图**。

- **有** → 留着它、不发 fatal 事件、`break`，并在返回的 `consistency.reason` 后面续一句
  "之后的重画没跑成（第 N 次：…），书上留的是第 M 次那张——它只是没通过比对，不是'没做出来'"。
  原始那句"哪一撮头发不对"一个字不动（`r_redraw` 与首次通过率要用它）。
- **没有**（第 1 次就没成）→ 照旧抛回 `illustrateAll`，那一页才是真的没有图。

★ 停手原因**不进 `errors`**：那个字段的口径是"这一页没有图"，而这一页有图。
两件事合成一条，以后就分不出"缺页"与"重画被打断"——同一条教训见 `index.ts` 里 `narrations` 那段
（"一个字段只有一种含义"）。

### 两个想过之后才这么写的决定

1. **产出失败后不再往下一次尝试**。"第 1 次彻底失败、第 2 次成功"**在现在的语义下不会发生**，
   而且不该发生：出图那一步是"生成 + 下载"一次调用，它抛出来时字节已经没了，
   再来一次就是重新付一次钱——而"服务端可能已经建单"正是 `ECONNRESET` 不许重试要防的事；
   至于重试安全的那几种（DNS / 连接被拒 / 连接超时），**已经在 `requestJson` 里重试过一次**，
   连着两次都是安全类失败说明那是中断不是抖动。
2. **锁脸没生效那一句仍然无条件抛**（没并进 `produceFailed`）。理由是它由**策略与能力**决定，
   同一个 provider 在同一个循环里不会第 1 次锁上、第 2 次没锁，所以实际只会在第 1 次触发——
   而那时手上必然没有旧图，两条路重合。保留"无条件抛"是为了让文件头第 2 条那句话
   不被降级路径咽下去。
