# 01 · ADR-0004 的 200 行翻案阈值：首周确认或推翻（🧭 codebase-design）

Status: **done**（2026-10-15：判决 = 翻案，Status 已改；落地另排 W3）
依赖：无（判决规则今天就能落纸）· 最后一个数来自 [07](07-streaming-text.md)
收口日：10/15 落规则，10/21 补完最后三分之一的数并改 ADR 状态

## 背景

[ADR-0004](../../../docs/adr/0004-no-vercel-ai-sdk.md) 留了一句翻案条件：

> 若 W2 首周实测发现"流式解析 + Schema 校验 + 重试"这三样自己写超过约 200 行且开始重复，
> 再引 `ai` 核心包（它是框架无关的，只用它的 `streamText` / `generateObject`，
> 不引 React 那一半）。ADR 状态就是为这种情况留的。

ADR 自己的 Status 写着 `proposed（W2 首周确认或推翻）`。这条不结，技术文档里
"选型理由"那一章就得留一个待定，而 #8（技术方案创新 8 分）正压在这类论证上。

**这条的难点不在量，在判据。"约 200 行"与"开始重复"都太软**——
软的判据在执行时一定会被当时的心情解释一遍。所以第一件事是把它钉死，
再拿数去喂它。

## 一、量法（先钉死，再量）

### 1.1 数什么行

**非空、非注释行**。命令可复现（仓库根）：

```bash
for f in <文件清单>; do
  echo "$f code=$(awk 'BEGIN{inb=0} {line=$0; sub(/\r$/,"",line); t=line; sub(/^[ \t]+/,"",t);
    if (inb) { if (t ~ /\*\//) {inb=0}; next }
    if (t ~ /^\/\*/) { if (t !~ /\*\//) inb=1; next }
    if (t=="" || t ~ /^\/\//) next; print }' "$f" | wc -l)"
done
```

★ 用非注释行而不是总行数，是因为这个仓库的注释密度极高（有的文件注释比代码多），
拿总行数喂这个判据等于用"我们爱写注释"去证明"我们该引依赖"。

### 1.2 哪些文件算"这三样"

| 那一样      | 文件                                                                                                                                                                    | 备注                                                                       |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Schema 校验 | `schemas/schema.ts`、`schemas/story.ts`                                                                                                                                 | 一份定义同时出 JSON Schema 与运行时校验                                    |
| 语义校验    | `engine/tree.ts`                                                                                                                                                        | Strictly 不算 Schema，但它是"校验"的第二半；**单独列出，便于两种口径都报** |
| 重试        | `engine/plan.ts`（带反馈的规划重试）、`engine/illustrate.ts` 的重试段、`providers/http.ts` 的 `shouldRetry`                                                             | 逐页重试与规划重试语义不同，不许相加后当作"重复"                           |
| 流式解析    | `engine/sse.ts`、`lib/book-stream.ts`（工单 02）、`providers/http.ts` 的流式段、`providers/openai-text.ts` 的 `stream()`、`engine/plan-stream.ts`（工单 07 的增量抽取） | 2026-10-15 已落地，逐文件行数见 §二之补                                    |

### 1.3 什么算"开始重复"（这一条最要紧）

判据：**同一条逻辑在两个以上地方各写了一遍，且改一处必须记得改另一处。**

不算：两处长得像但语义不同（例如规划重试要"把失败贴回 prompt"，逐页重试要"重新采样 + 视觉判分"——
抽公共函数的参数列表会比正文还长，那不是抽象，是一次绕路）。

★ 每一条重复**必须写出 file:line**。写不出来就是"感觉重复"，不许记进判决。
这条纪律与 README §五「测量这一层」第一类同源：**拿一个更弱的事实去回答一个更强的问题**
（"我觉得有点重复" ≠ "重复到该引依赖"）。

### 1.4 判决规则

ADR 原文是两个条件的 **AND**：

```
行数(三项) > 200  且  重复条数 ≥ 1   → 翻案：引 ai core（不引 React 那一半）
否则                                 → 维持：自写
```

执行时不许把它改成 OR。**行数条件今天就已经成立**（见下），
若按 OR 执行，判决在还没量重复之前就落地了——那就不是判据，是结论的伪装。

### 已量出的一处真实重复

```
openai-vision.ts:118  parseLooseJson()   找第一个平衡的 { }（只认大括号，返回 Record）
schemas/schema.ts:219 extractJson()      找第一个平衡的 JSON 值（认 { 与 [，返回 unknown）
```

两段是同一个扫描器（含字符串态与转义态的处理），手写了两遍。
使用者只有 `openai-vision.ts:72` 一处；`extractJson` 有 4 条测试
（`schema.test.ts:75–90`，含 `{"a":"}{"}` 这种边界），`parseLooseJson` **一条测试都没有**。

★ 这一处如果要处置，处置是**合并**（`parseLooseJson` 变成 `extractJson` 的薄包装，
返回 `Record | null`），不是引 `ai`。理由与 README §五 第一类同形：横评脚本与
`plan.ts` 分叉的代价是"表上的数字是另一条流水线的成绩"，处置是**把来源收敛到一处**，
而不是换一条流水线。

`lib/engine/sse.ts` 与它的测试是同一天从 `lib/sse.ts` 搬进引擎的（理由见那个文件的文件头），
所以它出现在这一行里——**搬的是归属，不是新写的代码**。

**流式解析小计 = 68 + 30 + 131 + 76 + 70 = 375 行**（原来的估计是"今天 0 行，还没写"）。

### 重复那一条：今天量到 1 处，另外新增的 1 处当场消除

| 处                          | file:line                                                                                        | 是不是真重复                                                                                        |
| --------------------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| 转义感知的括号扫描器        | `providers/openai-vision.ts:131` 的 `parseLooseJson` vs `schemas/schema.ts:219` 的 `extractJson` | **是**。同一段"扫深度、认转义、切出平衡片段再 `JSON.parse`"，改一处必须记得改另一处。已合并（见下） |
| SSE 分帧（跨 chunk 的半行） | 原来是 `lib/sse.ts` 一份、我新写的 `providers/http.ts` 里又一份                                  | **是**，而且是**今天新造出来的**。当场消除：`http.ts` 改用 `engine/sse.ts` 那同一份解码器           |

★ 第二条值得单独记一笔：**"我们自己会开始重复写同一样东西"这件事，今天真的发生了一次**，
发生在一个人（我）在同一天里写两处 SSE 解析的时候。它不是假想的风险，
而 ADR 那条判据要抓的正是这个形状。

**合并那处扫描器的记录**（工单 01 §四 要求"合并后测试仍全过"）：

- `parseLooseJson` 改成调用 `extractJson`，但**保留"从第一个 `{` 开始"这一步**——
  直接换成 `extractJson(text)` 会让 `[{"score":1}]` 这种回包先被认成数组、
  再被判成"不是对象"而丢掉，而老实现能从里面抠出那个对象。
  合并是为了少一份扫描器，不是为了顺手改行为。
- 新增 `providers/openai-vision.test.ts`（5 条），其中**"数组包对象"那条专门钉住上面这个行为**。
- 合并后 `pnpm test` **470 通过 / 41 文件**（本单开工时是 418 / 37）。

## 三、还要做的一件事：把"引了会省多少"也算出来

只看行数会得出"我们手写了 810 行、引依赖就省了"的错觉。判决的另一半是
**引 `ai` 之后哪些要重写**，逐条列。

### 3.1 读的是哪些东西（**不是凭记忆**）

| 来源         | 读到的版本/值                                                                                                                                                                            | 怎么读的                                                                   |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| npm registry | `ai` **7.0.141**（dist-tags：latest 7.0.141 / ai-v6 6.0.307 / ai-v5 5.0.277）                                                                                                            | `npm view ai version dist-tags`（2026-10-15）                              |
| npm registry | `ai` 的依赖：`@ai-sdk/gateway@4.0.114`、`@ai-sdk/provider@4.0.27`、`@ai-sdk/provider-utils@5.0.60`；**peer：`zod ^3.25.76                                                                |                                                                            | ^4.1.8`**；**没有 react peer** | `npm view ai dependencies peerDependencies` |
| npm registry | `ai` 解包体积 **8.2 MB**                                                                                                                                                                 | `npm view ai dist.unpackedSize`                                            |
| npm registry | `@ai-sdk/openai-compatible` **3.0.69**（自家的 OpenAI 兼容网关要用它；它自己也 peer 了 zod）                                                                                             | `npm view @ai-sdk/openai-compatible version dependencies peerDependencies` |
| 官方文档     | `streamText` 的参数里有 `timeout`（数字或对象）、`abortSignal`、`maxRetries`（缺省 2）、`streamRetries`（缺省 0）；结果对象上有 `textStream` / `text` / `usage` / `reasoning` / `output` | ai-sdk.dev `/docs/reference/ai-sdk-core/stream-text`                       |
| 官方文档     | `timeout` 的语义：`totalMs` = 整个调用；`chunkMs` = **两次有内容的输出之间的间隔**；`firstChunkMs` = 到第一个有内容的输出为止（**"传输层的动静不算数"**）                                | 同上                                                                       |
| 官方文档     | 结构化输出现在是 `generateText / streamText` + `Output.object({schema})`。**ADR 原文点名的 `generateObject` 这个名字，在这一页上已经没有了**                                             | ai-sdk.dev `/docs/reference/ai-sdk-core/output`                            |
| 官方文档     | `Output.object` 的 schema "Supports Zod schemas, **Standard JSON schemas**, and custom JSON schemas"——**能直接吃 JSON Schema**                                                           | 同上                                                                       |
| 官方文档     | schema 不合法时**抛 `NoObjectGeneratedError`**（错误对象带 `cause` / `text` / `response` / `usage`）；那一页**没有**任何"把失败原因喂回去重试"的机制                                     | 同上                                                                       |

★ 最后两条是这一节最要紧的，因为 §三 原本问的就是它们：
**"一份定义两用"保得住**（JSON Schema 直接可用），而**"带反馈的重试"它不给**。

### 3.2 逐条对照

| 我们已有的                           | 引 `ai` core 之后                                                                                                                                                 |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 事件协议 `events.ts`（三个消费者）   | 不受益（ADR-0004 第 3 条理由仍成立：通用消息模型喂不了 MCP/日志/界面三处）                                                                                        |
| `replay` 双适配器（ADR-0003）        | **要重做一遍**：`ai` 的 provider 抽象不认识"按提示词指纹回放落盘资产"。它只能套在 SDK 的模型接口外面，我们仍然得写                                                |
| `buildTree` 的树形语义               | 不受益（结构化输出只保证形状，保证不了"共读版必须有分支"）                                                                                                        |
| `AssetStore`（内存 / 磁盘）          | 不受益                                                                                                                                                            |
| registry 的 per-request `Env`        | **受益**，但要经 `@ai-sdk/openai-compatible` 传 base/key/model——**多两个包**（外加 zod）                                                                          |
| 错误分类（四种坏法分处置）           | 部分受益：`NoObjectGeneratedError` 带 `text`/`usage`（原文拿得到），但"预算被思考吃光"仍然要我们自己去 `text` 里判                                                |
| `schemas/schema.ts` 的"一份定义两用" | **保得住**（文档原话：吃 Standard JSON Schema）。★ 但**省不下它**：JSON Schema 还是要我们生成，能换掉的只有运行时校验那一半                                       |
| 带反馈的重试（`withFeedback`）       | **不受益**——而这正是判据 1 的主体：文档只写了抛错。`maxRetries` 管的是传输重试，不是"把失败贴回 prompt 再来一次"                                                  |
| 流式解析 + 两个超时                  | **受益**：v7 的 `timeout: { totalMs, chunkMs, firstChunkMs }` 与我们今天手搓的两个超时**同构**，还多一个 TTFT（`firstChunkMs`）——**这是"维持自写"最站不住的地方** |
| 增量抽取（`engine/plan-stream.ts`）  | 不受益：它是产品语义（哪些字段算闭合、一页算不算写完），不是流式解析                                                                                              |

**这一节的结论（不是判决）**：引 `ai` 换掉的是**传输那一层**
（今天量的 375 行里，`http.ts` 流式段 131 + `openai-text.stream()` 76 = 207 行）
加上结构化输出的**调用姿势**；换不掉 schema 定义、带反馈的重试、事件协议、离线回放、增量抽取。
代价是 3 个包（`ai` + `@ai-sdk/openai-compatible` + zod）+ 8.2 MB，
而 `ai` 自己还拖着 `@ai-sdk/gateway`（即使我们不用 Vercel 的网关）。

## 三之补 · 判决（2026-10-15）

**一句话结论：翻案（Status → `superseded`）。** 按 §1.4 那条 AND 规则，两个条件都成立：

| 条件       | 量到的东西                                                                                                                                                  |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 行数 > 200 | 流式 375 + Schema 320 + 重试 115 = **810**；加上 `tree.ts` 的口径是 **953**。命令与逐文件行数见 §二之补                                                     |
| 重复 ≥ 1   | **1 处**：`providers/openai-vision.ts:131` 与 `schemas/schema.ts:219` 是同一段"转义感知的括号扫描器"。★ 另有 1 处（SSE 分帧）是**今天新写出来的**，当场消除 |

判据不是我改成宽松的：它原文就是 AND，而**两个都成立**——这一点在写这份判决前已经反复确认过，
因为反过来（把 AND 当 OR）正好是这份工单 §1.4 明令禁止的那件事。

**判决说了什么、没说什么**——这两句必须分开写，否则下一个人会读成"我们已经在用 `ai` 了"：

1. **决定改了**：翻案条件一旦成立，ADR 原本那条"自己写"就不再是项目的决定。
   `docs/adr/0004-no-vercel-ai-sdk.md` 的 Status 已从 `proposed` 改成 `superseded`，
   并写清了替代范围。
2. **代码没动**：落地是**一单独立的工作**，不在本单的验收里（本单验收就是"判决 + Status"）。
   范围与代价见 §3.2——**换掉的只有传输那一层（207 行）+ 结构化输出的调用姿势**。

**为什么落地排在 W3 而不是现在**（这一条也要能被反对，所以给出理由是具体的）：

- W1 横评（`scripts/w1-text-bakeoff.mts` 那批数字）走的是**我们这条传输层**。
  换掉它，那批"通过率/时延"的数字就失去了同一性——要么重跑，要么在文档里加一句
  "这批数字是换之前量的"。**数字要能复现**（README §五 第一类）比省 200 行重要。
- 离线回放（ADR-0003）要重写成"套在 SDK 模型接口外面的一层"。它是演示那天的保险，
  在收口前动它，等于拿已经验过的通路换一个新写的通路。
- 换掉之后仍然**省不下** `schemas/schema.ts` 与带反馈的重试（§3.2 的两行），
  所以收益比行数看着的小。
