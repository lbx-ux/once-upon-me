# 01 · ADR-0004 的 200 行翻案阈值：首周确认或推翻（🧭 codebase-design）

Status: open
依赖：无（判决规则今天就能落纸）· 最后一个数来自 [07](07-streaming-text.md)
收口日：10/15 落规则，10/21 补完最后三分之一的数并改 ADR 状态

## 背景

[ADR-0004](../../../docs/adr/0004-no-vercel-ai-sdk.md) 留了一句翻案条件：

> 若 W2 首周实测发现"流式解析 + Schema 校验 + 重试"这三样自己写超过约 200 行且开始重复，
> 再引 `ai` 核心包（它是框架无关的，只用它的 `streamText` / `generateObject`，
> 不引 React 那一半）。ADR 状态就是为这种情况留的。

ADR 自己的 Status 写着 `proposed（W2 首周确认或推翻）`。这条不结，技术文档里
"选型理由"那一章就得留一个待定，而 #8（技术方案创新 8 分）正压在这类论证上。

**这条的难点不在量，在判据。"约 200 行"与"开始重复"都太软**——
软的判据在执行时一定会被当时的心情解释一遍。所以第一件事是把它钉死，
再拿数去喂它。

## 一、量法（先钉死，再量）

### 1.1 数什么行

**非空、非注释行**。命令可复现（仓库根）：

```bash
for f in <文件清单>; do
  echo "$f code=$(awk 'BEGIN{inb=0} {line=$0; sub(/\r$/,"",line); t=line; sub(/^[ \t]+/,"",t);
    if (inb) { if (t ~ /\*\//) {inb=0}; next }
    if (t ~ /^\/\*/) { if (t !~ /\*\//) inb=1; next }
    if (t=="" || t ~ /^\/\//) next; print }' "$f" | wc -l)"
done
```

★ 用非注释行而不是总行数，是因为这个仓库的注释密度极高（有的文件注释比代码多），
拿总行数喂这个判据等于用"我们爱写注释"去证明"我们该引依赖"。

### 1.2 哪些文件算"这三样"

| 那一样      | 文件                                                                                                        | 备注                                                                       |
| ----------- | ----------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Schema 校验 | `schemas/schema.ts`、`schemas/story.ts`                                                                     | 一份定义同时出 JSON Schema 与运行时校验                                    |
| 语义校验    | `engine/tree.ts`                                                                                            | Strictly 不算 Schema，但它是"校验"的第二半；**单独列出，便于两种口径都报** |
| 重试        | `engine/plan.ts`（带反馈的规划重试）、`engine/illustrate.ts` 的重试段、`providers/http.ts` 的 `shouldRetry` | 逐页重试与规划重试语义不同，不许相加后当作"重复"                           |
| 流式解析    | 工单 07 新增的 provider 流式增量解析 + 本工单 02 的 SSE 帧编解码                                            | 今天 **0 行**，还没写                                                      |

### 1.3 什么算"开始重复"（这一条最要紧）

判据：**同一条逻辑在两个以上地方各写了一遍，且改一处必须记得改另一处。**

不算：两处长得像但语义不同（例如规划重试要"把失败贴回 prompt"，逐页重试要"重新采样 + 视觉判分"——
抽公共函数的参数列表会比正文还长，那不是抽象，是一次绕路）。

★ 每一条重复**必须写出 file:line**。写不出来就是"感觉重复"，不许记进判决。
这条纪律与 README §五「测量这一层」第一类同源：**拿一个更弱的事实去回答一个更强的问题**
（"我觉得有点重复" ≠ "重复到该引依赖"）。

### 1.4 判决规则

ADR 原文是两个条件的 **AND**：

```
行数(三项) > 200  且  重复条数 ≥ 1   → 翻案：引 ai core（不引 React 那一半）
否则                                 → 维持：自写
```

执行时不许把它改成 OR。**行数条件今天就已经成立**（见下），
若按 OR 执行，判决在还没量重复之前就落地了——那就不是判据，是结论的伪装。

## 二、已经量出来的数（2026-10-13 晚，写 spec 时顺手量的）

| 文件                       | 总行 | 代码行（非空非注释）        |
| -------------------------- | ---- | --------------------------- |
| `schemas/schema.ts`        | 290  | **237**                     |
| `schemas/story.ts`         | 127  | **83**                      |
| `engine/tree.ts`           | 188  | **143**                     |
| `engine/plan.ts`           | 144  | **106**                     |
| `engine/illustrate.ts`     | 299  | **238**（整文件，含重试段） |
| `engine/providers/http.ts` | 276  | **213**（含 `shouldRetry`） |
| `engine/events.ts`         | 155  | 105                         |
| 流式解析                   | —    | **0**（工单 07 才写）       |

**结论（只针对行数条件）**：哪怕只算最严的口径（Schema 两件 + 树形校验 + 规划重试），
也是 237 + 83 + 143 + 106 = **569 行**，是阈值 200 的 2.8 倍。
行数条件不需要等到 07 落地就已经成立。

### 已量出的一处真实重复

```
openai-vision.ts:118  parseLooseJson()   找第一个平衡的 { }（只认大括号，返回 Record）
schemas/schema.ts:219 extractJson()      找第一个平衡的 JSON 值（认 { 与 [，返回 unknown）
```

两段是同一个扫描器（含字符串态与转义态的处理），手写了两遍。
使用者只有 `openai-vision.ts:72` 一处；`extractJson` 有 4 条测试
（`schema.test.ts:75–90`，含 `{"a":"}{"}` 这种边界），`parseLooseJson` **一条测试都没有**。

★ 这一处如果要处置，处置是**合并**（`parseLooseJson` 变成 `extractJson` 的薄包装，
返回 `Record | null`），不是引 `ai`。理由与 README §五 第一类同形：横评脚本与
`plan.ts` 分叉的代价是"表上的数字是另一条流水线的成绩"，处置是**把来源收敛到一处**，
而不是换一条流水线。

## 三、还要做的一件事：把"引了会省多少"也算出来

只看行数会得出"我们手写了 569 行、引依赖就省了"的错觉。判决的另一半是
**引 `ai` 之后哪些要重写**，逐条列：

| 我们已有的                         | 引 `ai` core 之后                                                                |
| ---------------------------------- | -------------------------------------------------------------------------------- |
| 事件协议 `events.ts`（三个消费者） | 不受益（ADR-0004 第 3 条理由：通用消息模型喂不了 MCP/日志/界面三处）             |
| `replay` 双适配器（ADR-0003）      | 要重做一遍——`ai` 的 provider 抽象不认识"按提示词指纹回放落盘资产"                |
| `buildTree` 的树形语义             | 不受益（`generateObject` 只保证形状，保证不了"共读版必须有分支"）                |
| `AssetStore`（内存 / 磁盘）        | 不受益                                                                           |
| registry 的 per-request `Env`      | **受益**（`ai` 支持每次调用传 key），但要核对它是否接受**任意 OpenAI 兼容 base** |
| 错误分类（四种坏法分处置）         | 部分受益，但要核对它的错误类型能否区分"预算被思考吃光"与"回包结构变了"           |

★ **不许凭记忆写这张表**。要读 `ai` 当前版本的文档与类型定义（不是 README 的转述），
并特别核一条：**它的 schema 输入是 zod 还是能直接吃 JSON Schema**。
若能直接吃，我们"一份定义两用"（`schema.ts` 同时出 JSON Schema 与运行时校验）
还能保住——那是这一层最深的设计（seam 文档里写着"第二深的模块"）；
若不能，翻案的代价里要加上"把 569 行 codec 换成 zod"。

这条也是本项目最容易重犯的错之一（README §五 第三类）：**送错值只证明字段名存在**。
拿"我印象里 `ai` 能用 JSON Schema"当依据，与当初送错值探"平台认不认字段"是同一个形状。
