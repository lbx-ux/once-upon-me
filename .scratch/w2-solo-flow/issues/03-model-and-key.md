# 03 · 创作流：模型与密钥（ADR-0008 的兑现处，per-request `Env`）

Status: done（2026-10-14；两处**没有**做到的事写在验收表里，不藏）
依赖：[02](02-event-stream-transport.md)（POST 的 body 就是它）、[04](04-creation-flow.md)（表单壳）

## 背景

[ADR-0008](../../../docs/adr/0008-model-and-key-provided-by-user.md) 把产品形态定为
**用户自己输入模型 + 自己提供 API key**。这件事不需要改引擎一行，因为它早就成立：
`registry.ts` 的 `Env` 是**参数**而不是 `process.env`，模型名零硬编码。
这一单要做的是把"用户填的表单"拼成**一张 per-request 的 `Env`**。

★ 这一单同时是"模型名零硬编码"这条纪律的验收现场：**如果为了让表单跑通而动了
`lib/engine/` 的任何一行，那就是这条纪律没做到位**——不是"顺手改一下"。

## 一、表单与默认推荐值

| 字段                    | 必填 | 预填（可改）                         | 说明                                    |
| ----------------------- | ---- | ------------------------------------ | --------------------------------------- |
| 文本模型 `LLM_MODEL`    | 是   | `qwen3.8-flash`（W1 横评的默认推荐） | 规划、改写、审核共用                    |
| 文本 API key            | 是   | 空                                   | 密码型输入框；不预填、不回显            |
| 图像模型 `IMAGE_MODEL`  | 是   | `qwen-image-2.0`（同上）             | 逐页插画 + 角色卡参考图                 |
| 图像 API key            | 是   | 空                                   | 可与文本同一个 key（同一家平台）        |
| 视觉模型 `VISION_MODEL` | 否   | 空                                   | 留空 → 引擎走"未核对"路径（不假装通过） |
| BASE_URL（文本/图像）   | 否   | `https://tokenrhythm.studio/v1`      | 换供应商只改这里                        |

★ 默认推荐值的来源是 W1 的横评实测（`docs/tech-selection.md` §7/§9），
但在 ADR-0008 之后它的身份是**默认值不是边界**：填别的模型必须能跑，
且跑出问题时的文案要能指导用户。这条决定了下面 §三。

### 拼 `Env`

```ts
// 纯函数，进工单 09 的 tdd 范围
toEnv(form): Record<string, string | undefined>
```

产出的 key 与 `registry.ts` 读的**完全一致**（`LLM_MODEL` / `LLM_API_KEY` /
`LLM_BASE_URL` / `LLM_MAX_TOKENS` / `LLM_THINKING` / `IMAGE_*` / `VISION_*`）。
表单上不出现的项（思考开关、预算、超时、单张成本）**不填**，让适配器的缺省值生效——
默认值里有实测教训（关思考、4096 预算、300s 视觉超时），表单把它们暴露给家长
只会制造新的坏配置。**但这些值必须可见**（工单 [08](08-design-system-and-baseline.md) 的
生成页脚注里写一行"思考已关 / 预算 4096"，口径照 `describeProviders` 的写法）。

## 二、密钥的"三不进"（这条不商量）

ADR-0008 原话：**只在内存里活一次请求的生命周期——不落盘、不进日志、不进录制文件**。

| 不进     | 具体到本仓库的位置                                                                    |
| -------- | ------------------------------------------------------------------------------------- |
| 不落盘   | 任何 `store.put*` 的入参；`books/<id>/book.json`；角色卡里那几条 `modelId` 只记模型名 |
| 不进日志 | `console.*`、Next 的请求日志、错误对象（`EngineError` 的 `message` 与 `detail`）      |
| 不进录制 | `providers/replay.ts` 的 manifest（它本来只录文本与图像字节，要**验**而不是**信**）   |

### 验收方式：一次真跑的产物全文搜索

跑完一本后，对 `.out/web/` 下全部文本文件 + 服务端日志文件做一次搜索：

```
搜什么：完整 key，以及 key 的前 8 个字符（防被截断后进日志）
搜哪些：books/**.json · books/**.jsonl · manifest.json · *.log · 终端输出（重定向到文件）
判据：命中 0 次
```

★ 为什么连**前 8 个字符**也搜：真要泄，泄的形态多半是
`Authorization: Bearer sk-abc123…` 被截断打印的那一段。只搜完整串等于只防最蠢的那种泄法。

★ 这条检查要做成**一个可重复跑的命令**（放 `scripts/`，一次真跑之后跑一次），
不是"我检查过了"。理由与 `auditManifest` 同源：能复现的自查才算自查。

### 顺带一次历史检查

`.env.local` 里的开发 key 是另一条线（README 已定：原件只写 `.env.local`），
但要确认 W1 的产物里没有它：`.out/` 下已经有一批真跑结果（`live/`、`live3/`、
`engine-run/`）。**同上一条检查，对这批历史产物跑一遍**——
它们不进仓库（`.out/` 已 gitignore），但会被拷出去做演示，拷出去之前要有结论。

## 三、错误消息从此有两个读者

这是 ADR-0008 里最容易被漏掉的一条后果。现状（`registry.ts`）：

```ts
;`${name} 未配置。真实密钥只写 .env.local（仓库公开，提交上去撤不回来）`
```

这句话是**对开发者说的**，说得对。但 BYO 之后，终端用户也会看到错误——
让家长去改 `.env.local` 是荒谬的。所以错误消息要分叉：

| 读者           | 场景                                  | 文案应该说的                                                       |
| -------------- | ------------------------------------- | ------------------------------------------------------------------ |
| 用户（表单）   | 401 → "你填的这个 key 这台服务器不认" | 检查有没有复制全、有没有多余空格；这家平台是否要实名/开额度        |
| 用户（表单）   | 404 / `model not found`               | 这个模型名在这家平台上不存在，或你的账号没有它的权限；给默认推荐名 |
| 用户（表单）   | 403                                   | **改参数无用**——这是灰度权限，要去找平台申请（W1 实测过这一条）    |
| 用户（表单）   | 429 / 超时                            | 换一个时段或换一个模型；这不是你填错了                             |
| 开发者（脚本） | `.env.local` 缺 key                   | 保留原话（只写 `.env.local`，仓库公开）                            |

**做法**：翻译放在 **app 层**，不放引擎里——引擎不认识"表单"这个说法。
`registry.ts` 抛的 `EngineError` 带 `code`（`provider-not-configured` 等），
app 层按 `code` + HTTP 状态（适配器已经把 hint 拼进 message）译成用户版。
★ 若发现只有 `message` 里那点信息不够翻译，那么该补的是**结构化字段**
（`EngineError` 加 `httpStatus` / `providerCode`），不是让 app 去正则匹配 message。
**正则匹配 message 就是让文案去当接口**——改一个字就坏。

## 四、验收

- [x] 表单能填、能改、能提交；默认推荐值预填（`qwen-image-2.0` / `qwen3.8-flash`）
      → 创作流第 3 步（**顺序改了**，见下"一处推翻了计划"）；实测被挡住时说的话是
      「还差：文本 API key、图像 API key」——缺什么当场说清
- [x] `toEnv` 是纯函数且有测试（工单 [09](09-validation-tdd.md)）→ `src/lib/creation/to-env.test.ts` 7 条
- [~] `lib/engine/` 的 diff 是**空的**——**没有做到**，如实列出来（都不是"为了表单改引擎"）：
  · `errors.ts` 加两个结构化字段 `httpStatus` / `providerCode`（§三 的分流靠它们，不靠匹配 message）
  · `providers/http.ts` 的 `failureToError` 把这两个字段填上
  · `index.ts` 加导出：`bookIdOf` / `bookDirOf` / `manifestPathOf`、`asEngineError`、
  `BOOK_FORMS` / `AgeBand` / `AnchorSlot`（app 层不该自己拼 `books/<id>/…` 或抄一份合法值表）
  · **两处真 bug**：① `buildCard` 把参考图 mime 写死成 `image/webp`，而实测出图是 PNG
  ——三方不一致会一路传到视觉比对的 data URL；② `CardStore.create` 的 `referenceBytes`
  在类型上是 `number & Uint8Array`（一个没有值能满足的类型），因为它没把 `BuildCardInput`
  的那个字段一起 Omit 掉；改它的三个调用方都在 `scripts/*.mts` 里，而 tsconfig 的 include
  是 `**/*.ts`——**.mts 根本不进闸门**，所以一直没被发现
  · 另加 `CardStore.create` 的 `previous` 入参（"换一版 = 新 revision，不覆盖"，ADR-0007 的兑现）
  ★ 判据本身没有被破坏：引擎里**没有**任何一处为了表单新增分支、写死模型名或绕过 registry
- [x] §二 的三不进检查脚本存在，并在一次真跑 + 一批历史产物上跑出"命中 0 次"
      → `scripts/check-secrets.mts`：`.out/web` + `public/demo`（8 个文本文件）
      与 `.out`（W1 历史产物，**47 个文本文件**）各跑一遍，两次都是 0 命中；
      每把 key 查完整值**与前 8 字符**两种形态
- [x] 填错 key → 界面上出现的是**用户版**文案；node 脚本缺 key → 仍是**开发者版**文案
      → 实测两条路都跑了：① 创作流第 3 步拿假 key 打一次真接口，
      平台回 **HTTP 401 · UNAUTHORIZED**，界面拿到的是
      「这台服务器不认你填的 API key。检查一下是不是复制全了、有没有多带空格…」
      ＋末尾附上供应商原文（**追加**，不替换——换掉它我们自己排障就看不到原文了）；
      ② 不带 env 直接 POST `/api/books` 时，引擎那句
      「LLM_API_KEY 未配置。真实密钥只写 .env.local」原样保留
- [~] 换一个用户自带的模型（不是默认推荐里的那两个）能跑起来；跑不起来时给出的是
  §三 那四类之一的可操作文案，而不是一坨原始 JSON
  → **只验了后半句**（上一条那个 401 就是"跑不起来时的文案"）。
  **前半句没验**：没有用一个**别的模型名**真跑过一整本——那要花调用，我先把它留在这里，
  等 [01](01-adr0004-threshold.md) 或 [05](05-generate-orchestration.md) 需要时一起跑
- [x] 空 key 提交时**不发请求**（表单层挡住），别让用户等一次注定 401 的调用
      → 实测：模型那一步不填 key 时，"下一步"直接给出缺项清单，**一次网络请求都没有**

### 一处推翻了计划（记下来，别让下一个人以为是笔误）

**"模型与密钥"排在"角色卡"之前**。产品定义是 Step 3 角色卡 / Step 4 形态与声音，
计划表里也把模型与密钥放在第 4 步，但**出形象要真的调一次图像接口**——
先出形象再填 key，第一次点必然失败。这不是推演，是实测：在第 3 步点「出一张形象」，
服务端回 `provider-not-configured`，界面上出现一句"回到上一步把 key 填上"，
**而那一步在下面**。顺序错了，错误文案就指向一个不存在的地方。

## Comments

**2026-10-14 · 落地记录**

- 用户版文案的**唯一出处**是 [`src/lib/provider-messages.ts`](../../../src/lib/provider-messages.ts)：
  按 `code` + `httpStatus` 分流，**不匹配 message**（message 是给人读的，改一个字就坏界面文案，
  而且这种坏法没有测试会红）。测试里每一个 message 都是乱写的，专门钉住这条。
- 顺手补的一处不一致：401 经引擎规约后 `code` 是 `provider-call-failed`，
  客户端只看 code 会判成"可重试"，于是会在"key 不对"下面贴一句"（可以再点一次）"。
  现在**可重试性与状态码都由服务端算好**（`userFailureOf`），随响应体一起给：
  凭据/模型名不对 → 400 + `retryable:false`，平台限流或故障 → 503/502 + `retryable:true`。
  文案与可重试性同源，才不会互相打脸。
- 密钥自查脚本只扫文本白名单后缀（`.json/.jsonl/.log/.sse/.md/...`），
  二进制媒体一律跳过——在一张 PNG 里"碰巧出现 key"不是需要防的事。
- 命中时**只报文件、行号与字节位置，不打印密钥本身**：一个为了查泄漏而把密钥打到屏幕上的工具，
  是这次泄漏的同谋。
