# 01 · 环上的 12 张落到墙上

Status: done
依赖：无（动的是首页 CTA 与 `/home` 的进场，两块都已交付）

## 一、机制（一句话）

首页那颗「开始创作」在切页前量下 12 张封面此刻在**视口**里的位置（中心 / 视觉宽 /
不透明度 / 旋转），切页之后由 `/home` 的主题墙**接着往下走**：那 12 格的起点不是
"从下面浮上来"，而是那些位置。数据层 `lib/theme-handoff.ts`，落点那一步由
`lib/useEnterTimeline.ts` 的 `arrival` 接管。

## 二、六处判断（每条都对应一个"为什么不那样做"）

1. **落点是墙上那 12 格本身**（真元素动），不是叠一层贴图。终点天然精确，
   也不存在"落地那一帧与真身对不齐"的交接。代价是卡片带着名字一起飞——那不是穿帮。
2. **对齐的是图心，不是卡心**：墙上一格 = 图 + 名字 + 主题词，卡心比图心低约 22px。
3. **退场走完才量、才 push**（200ms），不是"点了立刻 push"：热缓存下 RSC 三十几毫秒
   就回来，立刻 push 会把退场腰斩，过渡质量就取决于缓存冷热了。
4. **CTA 那一行不跟着淡出**：退场之后还要等一次 RSC，那时只剩一个转着的环、一个字都没有，
   读起来像坏了。它 120ms 后自己说「正在打开…」（沿用 `AppShell` 的 `PENDING_SHOW_AFTER_MS`）。
5. **模糊不跟着飞**：12 个元素每帧重新栅格化 0.6s，与 `backdrop-filter` / `video`
   那两次学费同一性质（README §五）。距离感由 scale + opacity 承担。
6. **墙上那一层要抬到输入卡上面**（`position: relative; z-index: 2`）：static 块画在
   定位元素**下面**，不抬的话卡片会在输入卡背后消失半秒——而"一路看得见"正是全部意义。

## 三、实测（预览面板，2026-10-16）

`preview_start` 起会话隔离的那个 dev server（3313）。**先数 rAF**：1.2 秒内 **0 次**
（`visibilityState` 报 `visible`，README §五 记过的那个伪装）——所以**动效没法在这里验**，
只能验静态事实与数据通路。

| 量                                                                    | 读数                                                                                                                                                         |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 首页预渲染/水合后的「开始创作」                                       | 真 `<a href="/home">`，文案「开始创作 →」                                                                                                                    |
| 环上 12 张的 `data-orbit-index`                                       | 12/12，无缺号                                                                                                                                                |
| 点下去之后首屏的 `data-leaving`                                       | `true`（退场态生效）                                                                                                                                         |
| §8 那条规则（读 CSSOM，不靠记忆）                                     | `.hero[data-leaving="true"] .hero__brand, .hero__typing, .hero__ambient, .hero__glow { transition: opacity 0.2s; opacity: 0; }` —— **`.hero__cta` 不在其中** |
| `.hero__ambient` / `.hero__glow` 的 opacity（掐掉 transition 读终点） | 0.58 → **0** · 1 → **0**                                                                                                                                     |
| CTA 在切页前                                                          | 文案换成「正在打开…」                                                                                                                                        |
| 切页后的 `location.pathname`                                          | `/home`，主题墙 12 格、`opacity` 全 1（终态，没有停在半透明）                                                                                                |
| ★ **接力载荷 vs 我自己量的一遍环几何**                                | 12 张逐张比对 `cx / cy / w / opacity / rot`：**最大差 0.00**（`deltas` 全为 0）                                                                              |

最后那一行是这一单唯一的硬证据，量法：点击**之前**在页面上独立量一遍 12 张的
`getBoundingClientRect` + 自己的 transform 矩阵，存进 `sessionStorage`（跨切页活着），
切页**之后**再与载荷逐张相减。之所以能精确到 0：面板里 rAF 冻结，环**根本没自转**，
所以点击前后几何一字未变。用的是**一次性探针**（`rememberThemes` 里临时挂到
`window` 上那三行），量完即删，没进仓库。

## 四、没验的（写在明处）

- **动效本身**：这个面板里验不了（下面的五、2 与 Comments 最后一条）。第一次拿到真帧时
  才发现它**一帧都没跑** —— 见 Comments「用户实测」那一条，根因与修法都在那里。
  修完在同一台 headless Chrome 里量到了飞行（`scale 1.465 → 1.0`、图宽 `235 → 160px`、
  `y 421 → 587`，约 0.7s 收敛）。
- **`prefers-reduced-motion`**：没有可用的模拟手段（同 06 那一单）。但它不必单独验——
  那一支什么都不播，而默认态就是终态。

## 五、量这个面板时顺手撞到的两件事（写下来免得下次当 bug）

1. **面板一开始的量出来是错的数**：`innerWidth/innerHeight` 报 **0**（`.hero` 仍有 1280 宽），
   于是 `clamp(214px, 19.1vw, 302px)` 里的 `19.1vw` 解析成 0、每张卡取了下限 214px，
   主题墙的栅格也塌成 45px 宽一列。
   ★ **先 `preview_resize` 到 1440×900 再量**就正常了：视口变成真 1440×900、
   `19.1vw` 解析成 291px、每张卡的投影倍数也落回该有的档（见下面 Comments 那条实测）。
   载荷比对不受影响（两边量的是同一个当下），但**版面读数必须先 resize**。
2. **`_next/static/webpack/*.hot-update.json` 一片 404** 是另一条会话在改文件造成的
   （webpack 换了 chunk 名，这个面板还拿着旧的），不是这一单的代码问题——同一批 404 里
   还有 `app/(studio)/layout.js`、`home/page.js` 那两条 `ERR_ABORTED`。

## Comments

- 2026-10-16 起手先看 mtime：`CreateLanding.tsx` / `create-landing.css` 在一分钟前被
  改过（另一条会话常驻这个工作区），所以全程定点 `Edit`，没有整文件重写。
  期间撞到两次它的 HMR 整页刷新，以及后来 `AppShell.tsx` 也被它改过一遍
  （我的侧栏那一段在它改完之后仍在，逐行对过）。
- ★ 中途改了一处判断：`captureRing` 的宽度一开始取 `offsetWidth × 自己那条 transform 的缩放`，
  量下来发现**环上的卡是被投影过的**——`.hero` 的 `perspective: 1400px` 配上每张卡
  自己的深度（`z = (d − .5)·360`，最深 ±180）。按公式 `1400/(1400 ∓ 180)` 是 1.147 / 0.886，
  1440×900 实测逐张（`包围盒 ÷ 旋转撑大 ÷ 未投影宽`）：

  | 卡（`data-orbit-index`） | z    | 旋转          | 投影倍数      |
  | ------------------------ | ---- | ------------- | ------------- |
  | 3（最近）                | +180 | 0°            | **1.140**     |
  | 2 / 4                    | +156 | −0.1° / 0.2°  | 1.124 / 1.121 |
  | 1（转 1.91°）/ 5         | +90  | 1.9° / 1.8°   | 1.080 / 1.048 |
  | 0 / 6                    | 0    | 0° / −1.2°    | 1.018 / 1.017 |
  | 9（最远）                | −180 | 4.3°          | **0.894**     |
  | 7 / 11                   | −90  | −3.8° / −3.1° | 0.956 / 0.933 |

  也就是**前排约 +14%、后排约 −11%**。用没投影过的尺寸起飞，切页那一帧前 6 张会凭空
  缩小一成多——而这条接力的全部意义就是"你刚才看到的那 12 张接着走"。改成
  `rect.width / rotInflation(rot)`：包围盒是投影过的（要的就是它），但也被旋转撑大了 4.7%
  （16:9 转 5.2°），所以除回去。`rotInflation()` 有纯函数测试。

- `EXIT_MS` 原本 export 了，dev 控制台念了 Fast Refresh 那条警告
  （一个组件模块同时导出值 → 只能整页刷新），改成模块内常量。
- 新增一条断言钉住**静默失效**：接力的选择器与 `ENTER_STEPS` 最后一步必须是同一个字符串
  （改一处不改另一处，接力会一声不响地不生效）。`theme-handoff.test.ts` 里。
- 收尾全量跑 `pnpm test` 时撞到过一次 **`VirtualAlloc failed` / `Worker exited unexpectedly`**：
  并行 fork 的 vitest worker 在这台机器上被抢光了虚拟内存（当时另一条会话的 dev server 也开着）。
  加 `--no-file-parallelism` 再跑一次 **642 条全过**——那是环境，不是这一单的代码。

- ★ **2026-10-16 用户实测：「我并没有感受到 12 张封面各自从刚才在环上的位置飞进主题墙自己那一格啊」。**
  我原先给这一单的结论是"代码与终态契约完成、动效在本环境验不了"——那句话本身没错，
  但它**掩盖了一个真 bug**：真帧里整条时间线**一帧都没跑**。用户的报告是对的。

  根因不在接力这一侧（起点算得没错，载荷比对又是 0.00），在 `useEnterTimeline`
  的**两行之间**：「只播一次」的闸门（`played` ref）立着，而 cleanup 里的 `mm.revert()`
  会把这条时间线**整条撤回**。effect 只要跑第二遍，第二遍撞上闸门当场 return，
  画面就停在**撤回之后**的状态——什么都不演，连默认进场也没有。

  dev 的 StrictMode 就是"挂载 → 卸载 → 再挂载"，所以**从首页点进来那一趟必然跑两遍**
  （直接打开 `/home` 只跑一遍）。实测（headless Chrome 直连 CDP，真帧）：

  | 路径                     | `runs` / `earlyReturn` / `mmCallback` | 墙上第一格                                            |
  | ------------------------ | ------------------------------------- | ----------------------------------------------------- |
  | 从首页点「开始创作」进来 | **2 / 1 / 1**                         | 从第一帧起就是终态（`opacity: 1`、`transform: none`） |
  | 直接打开 `/home`         | 1 / 0 / 1                             | `opacity 0.7 → 1`、`y 3.6 → 0`（默认进场）            |

  修法：cleanup 里把闸门放回去（`played.current = false`）。`played` 从此是
  "这一刻有没有一条**活的**时间线"，不是"这辈子演过没有"；组件一卸载 ref 就没了，
  路由内切回这一屏是全新实例，那一刻重播是**对的**。
  修完在同一台 headless Chrome 里量到飞行：墙第一格 `scale 1.465 → 1.0`、
  图宽 `235 → 160px`、`y 421 → 587`，约 0.7s 收敛；截图对上（途中一帧 + 落定一帧）。
  直接 `/home` 那一趟同时复查过没有回归（`opacity 0.86 → 1`、`y 1.64 → 0.04`）。

  **教训（写给下一个接这一单的人）**：这一单原先那句"动效验不了 → 结论只到契约"是**结论**，
  不是**判据**。用户报"看不到"时，正确动作不是回头再读一遍起点公式，是**去数帧**。
  顺带一条环境事实：预览面板 rAF 冻结，**要真帧只能自己起隔离 dev server + 直连
  headless Chrome 的 CDP**（`Page.addScriptToEvaluateOnNewDocument` 从文档第一帧起采样，
  否则会漏掉最要紧的起手那几帧）。
  ★ 另外：这一单原先写在下面 §五、1 的"面板几何是错的数"后来也修了口径——
  先 `preview_resize` 到 1440×900 再量就对了（`19.1vw` 解成 291px），
  但那只救几何，**不救动效**。
