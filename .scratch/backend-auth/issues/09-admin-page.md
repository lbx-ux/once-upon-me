# 09 —— 管理页 `/admin`

`Status:` **done**（2026-10-17；四条验收都过了。★ 本地站长号的口令要重置，见工单 Comments）

## 要做什么

一屏最小管理页（用户 2026-10-16 选的方案）：**列出所有人 + 四个开关当场改**。

- `src/app/(studio)/admin/page.tsx` + `src/components/admin/*`：工作台的一屏（带侧栏），
  服务端取数（走 BFF → Java `/api/admin/users`），客户端那部分只负责勾选与提交。
- 侧栏**只在 `role=ADMIN` 时**多出「管理」那一格（`NAV` 是常量，所以这一格按角色算，
  与底部那两副面孔同一个写法）。
- 每行显示：账号 / 昵称 / 注册时间 / 上次登录 / 四个开关（全量提交，见
  `PermissionPatch`——增量在并发下会变成"我以为我关掉的又开了"）。
- 顶部显示：**今天发出去的短信条数 / 每日硬顶**（"237 / 300"），
  以及**注册开关的当前状态（只读）**——
  ★ 只读是刻意的：一个能改"钱从哪儿出"的开关不该是网页上一个按钮。
  要改就动服务器上的 `/etc/xiaozhujue/api.yml`。
- 演示账号那一行要**标出来**（后端给了 `demoAccount` 这个名字）：它的口令是公开的、
  四个能力全开，这一屏正是"谁在花我的钱"该被看见的地方。

## 怎么算做完

- 管理员进得去、普通人打 `/admin` 看到的是"这一屏只有管理员能看"（不是一片空）。
- 勾掉某个人的「图像」→ 他那边（不重新登录）点「开始创作」就被告知没有权限。
- 页面上能看到短信用量与注册开关状态。

## 2026-10-17 扩：建号 / 停号 / 删号 / 重置别人的密码

用户这一刻的原话是「先完成管理用户的后台系统（给用户分配权限的）」，
并在三个可选项里全勾了（建号停号删号、每个用户的作品与用量、重置别人的密码）。

**后端已经做完**（`AdminController` + `AdminService`，9 条集成测试全绿）：

| 动作      | 端点                                   | 三条判断                                                                       |
| --------- | -------------------------------------- | ------------------------------------------------------------------------------ |
| 建号      | `POST /api/admin/users`                | 重名拒；口令下限与"自己设密码"同一条（`AccountRules`）；**四个能力一个都不开** |
| 停号/复号 | `PATCH /api/admin/users/{id}/status`   | 不能停自己；不能停最后一个**还能用的**管理员；停的那一刻顶密码代次             |
| 删号      | `DELETE /api/admin/users/{id}`         | 不能删自己；不能删最后一个管理员；**演示账号拒**（删了会自己长回来）           |
| 重置密码  | `PATCH /api/admin/users/{id}/password` | 口令不回显、不生成；顶密码代次 → 他那些旧票一起作废                            |

- `users.status`（`ACTIVE`/`DISABLED`）走 `SchemaUpgrades` 那张清单补，**不是**新加迁移框架。
- ★ 判据选的是**「停号对一张已经发出去的票当场生效」**：只在登录时判一次的实现，
  其余几条全绿而这一条必红。它第一版确实红了，而且红出了一个真问题——见下。
- ★ 两条**实测撞出来的**：
  1. 停号顺手顶了密码代次，于是 `requireUser` 里"密码改过了"那条先命中，
     报给用户的是**「密码改过了，请重新登录」**（他会拿同一个密码反复试，
     永远不知道自己被停用）。两句都是 401，但一句有用、一句误导。
     修法是**把状态那句排到密码代次那句前面**。
  2. 「最后的管理员」那条护栏第一版**把已经停用的管理员也算进去了**，
     于是 A 停用了 B 之后**删不掉 B**（"别的还能用的管理员"是 0），B 永远赖在列表里。
     判据改成"这个目标此刻算不算一个能用的管理员"。

**还没做**：BFF 那四条路由 + 管理页上的界面（按钮、建号表单、状态徽章）。
★ 另外「每个用户的作品与用量」这一项**依赖归属**（工单 16）：
不先把作品挂到人身上，这一格没有任何东西可显示。所以那一项排在归属之后。

## 2026-10-17 下午：BFF + 界面 + 权限申请，全部落地（端到端验过）

上面那格「还没做」做完了，而且和权限申请一起（见工单 15 之外的新增）：

**BFF（全部只转发，判据在 Java）**：
`POST /api/admin/users`（建号）、`PATCH …/status`、`DELETE …/{id}`（204 空体）、
`PATCH …/password`，加上权限申请的四条（见 `requests/`）。

**界面（`AdminScreen` + `RequestQueue`）**：

- 建号折在 `<details>` 里（日常动作是勾开关，建号一天一两次，不该占着头一屏）；
  口令框 `type=password`，建成即清空——它不该一直挂在这台电脑的屏幕上。
- 停号**不做**二次确认（可逆），删号**必须**确认且写**那个人的账号**
  ——一条行与另一条长得几乎一样，而确认框的作用全靠它还能让人认真读一次。
- 演示账号的删除按钮**禁用**（`title` 写原因），不是藏——`AccountSeeder` 会把它补回来，
  按下去会自己撤销的按钮比没有按钮坏。
- 停用的行整行淡下去（`tr[data-status='DISABLED']`），四个开关**禁用**但不藏：
  他明天被恢复时，那些开关本来就该是他停用前的样子。

**权限申请**（替掉帮助弹窗里那句"发邮件到 …"，Java 侧见
`PermissionRequestController` / `PermissionRequestService` / `AdminRequestRow`）：

- 用户那一半在帮助弹窗里：四个复选框 + 一句说明 + 发出去。**已经提过**的那个人看到的是
  "你已经提过一条了"，**没有提交按钮**——否则他会连提三次，而服务端并成一条
  恰恰说明界面在骗他"没提交成功"。
- 管理那一半在管理页顶上：每张卡片显示**是谁**（昵称/打码手机号 + 账号 + 时间）、
  「他已有的」与「这次要的」**两格并排**（批准 = 并上不是换成，只看"要的"
  会让站长以为自己把他已有的关了）、他写的那句话，和 给他开 / 拒绝。
- 申请行上带 `current`（这个人现在手里的四个开关），由 Java 一起查出来——
  没有它，"这次批准会改变什么"就只能靠猜。
- 被拒的那条**留在**列表里（折在"处理过的"下面）：不留的话申请人会反复提、
  站长会反复拒，两边都以为对方忘了。

**★ 端到端验证撞出来的那个 bug（这就是为什么要真跑）**：
删掉一个**提过申请**的号，`permission_requests` 里那几行不会跟着走——
账号没了，那一行的 `account` 变成空串，而空串在前端 `parseRequestRow` 里是
"这一行读不出来"，于是**整列申请**渲染成"读不到申请列表"。
一个人被删掉，其余所有人的申请跟着看不见。
修法：`AdminService#deleteUser` 把 `permission_requests` 一起删（这个库没有外键、
没有级联，"一起删"必须在代码里写出来），并有
`AdminUsersIntegrationTest#deletingAnApplicantDoesNotBreakTheRequestList`
钉住——**判据是"别人那条还在"**，因为"列表是空的"在两种实现下都成立，
分不出"跟着删"与"留成孤儿"。

验证方式记录（复现要照这个来）：

- 前端 830 测试全绿；后端 74 全绿（新增 `PermissionRequestIntegrationTest` 9 条）。
- **打真 HTTP 面**的脚本在 `.out/verify-permreq.mjs` / `.out/verify-delete.mjs`
  （起自己的 Java 在 8099、自己的 Next 在 3312，`BACKEND_URL` 指过去；
  ★ Java 要带上与 `.env.local` 同一个 `APP_JWT_SECRET` 起动——不带的话它生成
  一把随机的，Next 验不了它的票，所有请求 401，而那时第一反应会以为是自己写错了）。
- 测试账号与申请行验完即删（共享的 H2 文件库，不能弄脏）。

## 2026-10-17 傍晚：管理页能换模型 / 接口地址 / api-key

用户的原话：「就在管理端加一个功能，就是可以更换模型、更换模型的 api 网站、更换模型的 api-key」。
在这之前换一次模型要 SSH 上去改 `.env.local` 再重启 Next。

**形状**：那一屏是**四个能力 × 各三格**（文字 / 图像 / 视觉 / 语音，每格 模型名 / 接口地址 / API key，
语音多一格音色）。每一行顶上显示**引擎自己那一句话**（`describeProviders(serverEnv())`，
原本是给 `/api/health` 写的自检，一直没有调用方）——所以"管理页上写着的"与"引擎实际会做的"
是同一句，而不是这一层重新拼一份。

**四条判断**（都写在 `ModelConfig.tsx` 与 `model-config.ts` 的文件头）：

1. **key 只进不出**。`modelConfigView` 对秘密那一格永远只回"配没配 + 从哪儿来的"，
   不回值。代价是站长看不出"现在这把是哪一个"——那是**故意**选的那一边：
   key 填错会立刻 401 暴露，key 泄出去不会。端到端那条判据是把 `.env.local` 里
   5 个真值读出来、在整个响应体里搜，一个字节都不许出现。
2. **空 = 这次不改**，清空是另一个动作（「恢复默认」）。合成一件的话，只想换模型名的人
   会把 key 一起清掉，而症状要到下一次生成才出现（401）。
3. **改完立刻生效，不用重启**：`serverEnv()` 每次调用现读那份文件（它本来就不做缓存，
   那条注释现在的理由更强了）。判据选的是 `GET /api/auth/me` 里的 `speechModel`——
   它由**引擎那一侧**现读 `TTS_MODEL` 给出来，所以"文件写进去了"与"真的生效了"
   是两件事，只有后者能让这条变绿。
4. **落点在磁盘上、被 gitignore**（`models.runtime.json`，`MODEL_CONFIG_FILE` 可改），
   写入是"临时文件 + rename"，权限 0600。它是**全站生成的配置来源**，
   写到一半断电留下半个 JSON 等于全站坏掉。读**永不抛错**（坏 JSON 当没有覆盖、
   退回环境变量，并 `console.error` 按 mtime 去重），理由同上：为一份手改坏的文件
   让全站 500 是把小事故升级成大事故。

**★ 端到端验出来的一个 bug（第一版真的错了）**：路由里遍历的是**全部四个字段名**，
于是「语音」有而别人没有的 `voice` 让**文字/图像/视觉三个能力的保存全部 400**——
只有语音是通的。而当时那条"给文字送 voice → 400"的用例**照样绿**，
因为它期望的就是 400，只是绿的**理由**是错的。修法是只校验这个能力真有的那几格，
多出来的字段仍然拒（拼错字段名必须说出来）；我自己那几条正例（只改 image 的模型名）
逮住了它。这一条值得记：**一条期望 400 的用例，如果不问"为什么是 400"，会盖住一整类 bug。**

**★ Java 侧只加了一个 `GET /api/admin/check`**（`requireAdminFresh` + 返回 `{admin:true}`）：
那份配置只在 Next 一侧存在（ADR-0009），Java 碰不到文件，所以"给不给写"这件事
需要一个服务端的出处。不在 Next 那一层自己看票里的 `role`——那是**签发时**的角色，
而被停用、改过密码的人旧票照样说他还是管理员；那两条判据只有 Java 那一份。

## 2026-10-17 傍晚（同一轮，用户中途改的口径）：申请不再分项

用户：「申请的时候这些功能是一起发放的，申请的时候申请一下就行了」。

- 帮助弹窗里那四个复选框**撤了**，只剩一句说明 + 发出去。「至少勾一项」那句提示
  跟着撤——它要挡的情形（一样都没勾）在申请恒为四项之后已经不存在了。
- `POST /api/permission-requests` 的请求体**只剩 `{note}`**；服务端把四列一律写成真。
  库里那四列留着，它记的是"这一条申请要开什么"，于是下游不必去猜"没有 wants 是什么意思"。
- `Permissions.empty()` 与 `asks-for-nothing` 随之删掉（没有调用方了，留着会让人以为
  某处还在靠它挡着什么）。
- 管理页那张申请卡：右边那一格从「这次要的」改成**「开通之后：全部四项」**——
  它现在是常量，写成"申请人挑的"会让站长以为这个人只想要其中几项。
- ★ `approvingMergesInsteadOfReplacing` 那条测试**改名并改了判据**（现在是
  `approvingGrantsAllFour`）：申请恒为四项之后，"并上"与"换成"结果**完全一样**，
  那条用例再也分不出这两者。留着那个名字就是一条**声称有判别力、实际没有**的判据——
  那比没有测试更坏。`decide` 里那段合并留着（"绝不拿走已有权限"这条不变式仍然值得守），
  但注释里写明了它现在不靠这条测试守着。
