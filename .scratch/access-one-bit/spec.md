# spec：权限收成一位（2026-10-18）

## 用户要的

> 现在更新一下，没有登录的人是没有权限进行创作，但是登录之后就可以使用各种模型了，
> 不用站长分配，在站长的管理那，还是可以看到用户传作了几本，有几个人物，后面的选项
> 就变为是否有权限，默认注册的用户都有权限，所以给"帮助"那个模块删除吧

## 改后的语义

一个人**有没有创作权**只剩一位 `allowed`：

- **注册 / 建号 = 给上**（`true`）。这就是"登录之后就能用各种模型"。
- 站长在管理页把它关掉 ⇒ `false`。他下一次点「开始创作」被拦，那句话照旧是
  「当前用户没有权限，请联系管理员」（用户 2026-10-16 定的原话，不改）。
- 未登录 = 没有权限。这一条本来就是这样（`requireCapability` 先判登录），不改。

「能力」这个词没有消失，但它只剩两种用法，都**不是**"这个人有没有"：

| 用法                                     | 是什么                                               | 谁给                               |
| ---------------------------------------- | ---------------------------------------------------- | ---------------------------------- |
| `configured.text/image/…`                | **站里配没配**这一项（密钥在不在），四项仍然各自独立 | `serverEnv()`（Next 的服务端环境） |
| `requireCapability(req, caps)` 的 `caps` | **这条路由要什么**能力                               | 路由自己                           |

而"这个人有没有"这一位，四个能力**同真同假**：政策是"有权限 = 四项都能用"。
这句话只写在那道闸一处，不让三十个调用点各写一遍。

## 三个决定

1. **申请那整套一并删掉**（用户端表单 + 管理页申请队列 + 两条 BFF 路由 + Java 的
   `PermissionRequest*` + 库表）。理由：默认给上之后没有人需要申请，
   而一个永远收不到东西的队列比没有这一栏更坏——它会让人以为"是不是没人找过我"。
2. **帮助弹窗里另外三条说明一起删**（谁配的密钥 / 为什么看不到别人的书 / 数据在服务器上只租 6 个月）。
   用户要求删的是整个模块。
3. **老账号自动给上**。补列时 `DEFAULT 1`，于是截图里那批"四个全关"的号一次变成「有权限」。
   他们当初是全关的，只因为那时候要站长手工开。

## 库怎么改（只加不删）

- `schema.sql`：`user_permissions` 由四列收成一列 `allowed TINYINT NOT NULL DEFAULT 1`；
  `permission_requests` 建表语句删掉（新库不再有这张表）。
- `SchemaUpgrades`：给**已经建过**的库补 `allowed TINYINT NOT NULL DEFAULT 1`。
  `DEFAULT 1` 就是"老账号自动给上"那一句的落地。
- ★ 老库上那四列 `can_*` 与 `permission_requests` 表**留着不动**——`SchemaUpgrades`
  刻意不做 DROP（"启动时按代码重排你的库"是会吃掉数据的动作）。
  于是老库上会有几列/一张表没有代码再读写它们，这是这笔取舍的代价，写在这里。

## 判据（只有真做才会不同）

- 未登录 `POST /api/books` → 401；登录（演示账号）→ 不是 403。
- 站长关掉权限之后，用**同一张旧 cookie** 打 `POST /api/books` → 403 `no-permission`
  （证明是"下次点开始创作就生效"，不是"等他重新登录"）。
- 老库补列之后，老账号那一行是「有权限」（`SchemaUpgradesTest` 里钉住"老行 = 1"）。
